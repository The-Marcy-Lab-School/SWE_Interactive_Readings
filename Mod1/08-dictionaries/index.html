The City That Wasn't in the Dictionary

~20 minutes Interactive No setup needed to read

1. The lookup that crashed

Weather apps get their numbers from a weather API (Application Programming Interface), which is a service you ask over the internet for data. Here is part of what OpenWeatherMap, a real weather-data service many apps build on, sends back when asked about Brooklyn. It arrives as JSON (JavaScript Object Notation), the text format most APIs answer in:

{
  "name": "Brooklyn",
  "main": {
    "temp": 71.6,
    "humidity": 58
  },
  "weather": [
    {"description": "scattered clouds"}
  ]
}

Once Python reads that response, it is a dictionary. A dictionary stores data as key and value pairs instead of numbered positions. Curly braces hold the pairs. Each key is a name, and each value is the data stored under that name. response["name"] gives back "Brooklyn", and response["main"]["temp"] gives back 71.6.

A small tool built on that API keeps its own dictionary of temperatures it has already fetched, so it never asks for the same city twice in one session:

cached_temps = {
    "Brooklyn": 71.6,
    "Queens": 68.2,
    "Bronx": 69.5,
}

Someone typed "Manhattan," the tool ran cached_temps["Manhattan"], and Python stopped there:

Traceback (most recent call last):
  File "weather_app.py", line 12, in <module>
KeyError: 'Manhattan'

Nothing after that line ran. No temperature, and no "sorry, no data for that city" message either. The rest of this reading is the set of dictionary moves that tool needs: reading a value when the key might be missing, adding and removing cities as people search, looping over everything cached so far, and storing a whole list of cities at once.

3. Reading a value when the key might be missing

Bracket notation is the direct way to read a value, and it is the right choice whenever the key is guaranteed to be there. Every OpenWeatherMap response carries a "name" key, so response["name"] is safe. A city someone just typed is a different story. Here are both lookups on the same dictionary:

Brackets, on a key that is missing

cached_temps = {
    "Brooklyn": 71.6,
    "Queens": 68.2,
    "Bronx": 69.5,
}

print(cached_temps["Manhattan"])
print("still running")

It printed:

KeyError: 'Manhattan'

.get(), on the same dictionary

cached_temps = {
    "Brooklyn": 71.6,
    "Queens": 68.2,
    "Bronx": 69.5,
}

print(cached_temps.get("Manhattan"))
print(cached_temps.get("Manhattan", 0))
print(cached_temps.get("Brooklyn"))

It printed:

None
0
71.6

The bracket version never reached print("still running"). A KeyError ends the program on the spot. The .get() version ran all three lines. Called with one argument, .get() gives back None for a key it cannot find. Called with two, it gives back the second argument instead, which is why the middle line printed 0. On a key that is there, .get() behaves exactly like brackets and hands over the value.

There is a third option when you want to decide for yourself. The in operator on a dictionary searches the keys, so "Brooklyn" in cached_temps is True and "Manhattan" in cached_temps is False. Use it when a missing key needs its own branch of code rather than a fallback value.

4. Adding, changing, and removing pairs

A cache that can never grow is not a cache. Every time someone searches a new city, the tool has to put that city into cached_temps, and every so often it has to throw a stale one out. Dictionaries are mutable, which means Python can change the pairs inside a dictionary that already exists. Four moves cover all of it:

  • cached_temps["Manhattan"] = 70.1 adds the pair when "Manhattan" is a new key.
  • cached_temps["Queens"] = 68.9 replaces the value when "Queens" is already a key. The same line does both jobs, and which one happens depends only on whether the key is already in the dictionary.
  • del cached_temps["Bronx"] removes the pair. del is a statement rather than a method, so it has no dot and no parentheses.
  • cached_temps.pop("Brooklyn") removes the pair and hands back the value it removed, which is useful when you want to use that value one last time.

The key inside the brackets is an expression, so it does not have to be typed out as a literal string. A variable works just as well, and that is what makes a search box possible: the tool never knows the city name while the code is being written.

A key typed as a literal

cached_temps["Manhattan"] = 70.1

A key held in a variable

city = input("Which city? ")
cached_temps[city] = 70.1

Both lines add one pair. In the variable version, Python works out what city holds first, then uses that string as the key. Typing Manhattan at the prompt gives the two lines the same result.

Here are all four moves in a row, starting from the three cached cities:

cached_temps = {"Brooklyn": 71.6, "Queens": 68.2, "Bronx": 69.5}

city = "Manhattan"
cached_temps[city] = 70.1
cached_temps["Queens"] = 68.9
del cached_temps["Bronx"]
dropped = cached_temps.pop("Brooklyn")

5. Two names, one dictionary

The tool outgrew a plain number per city. Each saved city is now its own dictionary, with a list of active weather alerts inside it. A dictionary holding lists and other dictionaries is called nested data:

brooklyn = {
    "name": "Brooklyn",
    "temp": 71.6,
    "alerts": ["heat advisory"],
}

A variable does not hold a dictionary. It holds a reference to one, exactly as it does with a list. Assigning that variable to a second name gives one dictionary two names, and a change made through either name shows through both:

The code

saved = brooklyn
saved["temp"] = 80.4

print(brooklyn["temp"])
print(brooklyn is saved)

What it printed

80.4
True

saved = brooklyn builds no second dictionary. It gives the one dictionary another name, and brooklyn is saved reports True because both names refer to the same object. To get a real second dictionary, copy it. dict(brooklyn), brooklyn.copy(), and {**brooklyn} all do the same job, and you will see all three in other people's code.

The copy that was not a copy

The tool has a function that is supposed to be pure: hand it a city and an alert, and it hands back a new city dictionary carrying that alert, leaving the original alone. It copies first, which looks like exactly the right move:

with_alert, copying the dictionary

def with_alert(city, alert):
    clone = dict(city)
    clone["alerts"].append(alert)
    return clone

updated = with_alert(brooklyn, "flood watch")

print(brooklyn["alerts"])
print(updated["alerts"])

What it printed

['heat advisory', 'flood watch']
['heat advisory', 'flood watch']

The original picked up the flood watch too. Here is the rule that explains it. dict(), .copy(), and {**city} each build a new outer dictionary and then store the same values in it. A string or a number is immutable, so sharing one is harmless. A list is mutable, and the copy stores a reference to the very same list the original holds. clone["alerts"] and brooklyn["alerts"] are two routes to one list, so .append() through either route adds to it once and both routes see it.

The fix is to copy the inner list as well, before anything appends to it. Both versions of with_alert are here so the one changed line is easy to find:

Impure
copies the dictionary only

def with_alert(city, alert):
    clone = dict(city)
    clone["alerts"].append(alert)
    return clone

Pure
copies the nested list too

def with_alert(city, alert):
    clone = dict(city)
    clone["alerts"] = list(city["alerts"])
    clone["alerts"].append(alert)
    return clone

With the extra line, the pure version printed ['heat advisory'] for brooklyn and ['heat advisory', 'flood watch'] for updated. This trap is worth remembering because of how quietly it fails. A function that copies first looks pure, passes a quick read, and still edits data somewhere else in the program.

6. Looping over a dictionary

The tool shows a panel listing every city it has cached, which means walking the whole dictionary rather than asking for one key. A for loop over a dictionary visits the keys, one per pass:

The code

cached_temps = {"Brooklyn": 71.6,
                "Queens": 68.2,
                "Bronx": 69.5}

for city in cached_temps:
    print(city)

What it printed

Brooklyn
Queens
Bronx

Three methods give you exactly the part you want. .keys() gives every key, .values() gives every value, and .items() gives each key and its value together. .items() is the one you will reach for most, because the for line can unpack the pair into two names at once:

Values only

for temp in cached_temps.values():
    print(temp)

It printed:

71.6
68.2
69.5

Both halves, unpacked

for city, temp in cached_temps.items():
    print(f"{city} is {temp} degrees")

It printed:

Brooklyn is 71.6 degrees
Queens is 68.2 degrees
Bronx is 69.5 degrees

Each pass of .items() produces one key and one value, and for city, temp puts them into two separate names. That is the same unpacking enumerate() uses for a list.

One thing surprises people about .keys(). It does not give back a list:

The code

print(cached_temps.keys())
print(len(cached_temps))
print(list(cached_temps.keys())[0])

What it printed

dict_keys(['Brooklyn', 'Queens', 'Bronx'])
3
Brooklyn

.keys() gives back a dict_keys object. A for loop can walk it and in can search it, and that covers almost everything anyone does with keys. Brackets cannot index it, so cached_temps.keys()[0] raises a TypeError. Wrapping it in list() builds a real list, which is what makes the third line work. len() on the dictionary itself counts the pairs, so no method call is needed there at all.

cached_temps holds three pairs: Brooklyn 71.6, Queens 68.2, and Bronx 69.5. Check every statement that is true.

7. Many cities, one list

A city is more than a temperature now, and the tool has to hold several of them at once. The shape that does this is a list where every element is a dictionary with the same keys. It is how a program holds many of the same kind of thing:

saved_cities = [
    {"name": "Brooklyn", "temp": 71.6, "starred": True},
    {"name": "Queens", "temp": 68.2, "starred": False},
    {"name": "Bronx", "temp": 69.5, "starred": False},
]

The list keeps the cities in order, and each dictionary keeps one city's fields labelled. Looping over the list hands you one whole dictionary per pass, and bracket notation reads a key off it:

The code

for city in saved_cities:
    print(f"{city['name']}: {city['temp']}")

print(saved_cities[1]["name"])

What it printed

Brooklyn: 71.6
Queens: 68.2
Bronx: 69.5
Queens

saved_cities[1]["name"] reads as "element 1 of the list, then the "name" key of that dictionary". The index picks which thing, and the key picks which field of it. Note the single quotes inside the f-string: the f-string itself is wrapped in double quotes, so the key inside it uses the other kind.

Growing the list uses the same list method as any other list, with a whole dictionary as the value:

saved_cities.append({"name": "Manhattan", "temp": 70.1, "starred": False})

After that line saved_cities holds four dictionaries, and the for loop prints four lines without a single change.

8. Summary and reflection

A dictionary stores data as key-value pairs, which is the shape of most "look something up by name" data, a JSON response included. Brackets read a value and are the right choice when the key is guaranteed to exist. .get() is the choice when it might not, because it gives back None or a default you pick instead of raising a KeyError. Dictionaries are mutable, so assignment adds or replaces a pair, and del or .pop() removes one, with the key written as a literal or held in a variable. A for loop visits the keys, .items() hands over each key and value together, and .keys() gives a dict_keys object rather than a list. A variable holds a reference to a dictionary, and dict() copies the outer dictionary while leaving every nested list or dictionary shared. A list of dictionaries is how a program holds many of the same kind of thing.
