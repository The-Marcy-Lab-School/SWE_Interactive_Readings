Run It Before You Read It

~20 minutes Interactive No setup needed to read

1. A program nobody can explain

Lend-a-Hand is a small Python program that a community tool library uses to track what is on its shelf. A tool library lends out drills and ladders the way a book library lends out books. One volunteer wrote Lend-a-Hand, ran it for a year, and then moved away. Now another volunteer has filed a bug: "It won't let me lend out the sander."

You have two files and nothing else. No notes, no comments, nobody to ask. Opening the first file and reading from the top is how most people start, and it is also how most people get lost. A screen or two in, you are holding half a dozen facts you only half believe, and you can no longer say which ones you actually checked.

There is a better order to do this in, and it starts by not reading. It is the same order whether a teammate, a library's author, or an AI model wrote the lines.

3. Step 1: run it before you read it

Run the program and use it, before you open a file. Give it good input. Give it bad input. Try to break it. What comes back are facts about what Lend-a-Hand does, and every line you read afterward has to agree with those facts.

Reading first builds a picture of what you think the program does. Then you run it, something comes out that does not match, and you can miss it, because you already believe you know the answer. Running first means the surprise arrives while you can still see it.

This Terminal runs the real commands, and the real Lend-a-Hand program, against a copy of the volunteer's folder. Each line you type is echoed after the folder name, and the program's questions come out underneath it. Work through these in order.

  1. ls — see which files the volunteer left behind
  2. python3 main.py — start the program
  3. 3 — pick Report, and read what is on the shelf
  4. 2, then sander, then 1 — try to lend the sander, which is what the bug report is about
  5. 2, then drill, then two — hand it a word where it wants a number, then keep typing and see where you end up
  6. 4 — quit
What else can I try in there?

Try to lend a tool the library has never owned, such as 2, then chainsaw, then 1. Try lending more drills than the shelf holds. Pick 1 to add three of something new, then pick 3 and see whether it shows up. Quit with 4, start the program again, and pick 3 a second time to find out whether Lend-a-Hand remembers anything between runs.

Compare with one possible answer

Something like: "It keeps a count of how many of each tool the library has on the shelf, lets you add to a count or lend tools out, and prints the list."

That is the answer to the first orientation question, and you wrote it without reading any code. Everything you read from here on has to agree with that sentence. If something does not agree, either the sentence is wrong or you have found a bug, and either one is worth knowing.

4. Steps 2 and 3: the entry point, the map, and the data

The entry point is the file you hand to python3, and, inside it, the function that starts everything. In a Python program you already know the two things to look for: the if __name__ == "__main__": guard, and the main() it calls.

Then list the files. For each one, read only the import lines and the def lines, and write one sentence about what that file is for. Leave the bodies alone for now. You are drawing a map, not walking the ground.

Here is every import line, every def line, and every top-level variable in both of Lend-a-Hand's files, with the line number each one sits on:

main.py:1:from shelf import add, lend, report
main.py:4:def main():
main.py:32:if __name__ == "__main__":

shelf.py:1:shelf = {"ladder": 1, "drill": 2, "sander": 0}
shelf.py:4:def add(name, quantity):
shelf.py:9:def lend(name, quantity):
shelf.py:18:def report():

That is the map. main.py carries the __main__ guard, so main.py is the file you run and main() is where the program starts. main.py is for talking to the volunteer. shelf.py is for keeping and changing the shelf.

Step 3 asks a different question: what does this program remember? Find every variable that lives at the top level of a file, and write down its shape. "A dictionary from a tool's name to how many are on the shelf" is a shape. Once you know the shape, every function turns into a short question: what does this one do to shelf?

Lend-a-Hand has exactly one piece of data that lives between actions: shelf, on the first line of shelf.py. Its shape is a dictionary from a tool's name, a string, to a count, an int. Everything the program does is either a change to that one dictionary or a report on it.

You have read only the import lines, the def lines, and the shelf line. Check every statement you can honestly put in your "I know" column.

Need a hint?

For each statement, ask which line you read it off. Three of the five come straight off a line you have seen. The other two come from a function's name, and a name is the author's claim about the code, not the code.

Two of those five statements are guesses wearing the clothes of facts, and both came from a function's name. A function's name and its parameter list are the author's notes to you about intent. lend(name, quantity) says "I lend some quantity of a named tool," which is real information and belongs in your notes. Only the body tells you whether the code lives up to the name, so until you read the body, a claim off a name goes in the "guessing" column.

5. Step 4: trace one action from input to output

Pick one thing a person can do, start at the entry point, and follow that single action through every function it touches, in order, until the output appears. Ignore every other branch. You will come back for them. Trying to hold a whole program in your head at once is how you get lost.

The bug report said the sander will not lend, so trace that one action: choose 2, type sander, type 1. Here are both files in full. This is the first point in the method where you read a body.

main.py
talks to the volunteer

from shelf import add, lend, report


def main():
    print("Lend-a-Hand: the tool shelf.")
    while True:
        print("\n1. Add  2. Lend  3. Report  4. Quit")
        choice = input("Choose (1-4): ").strip()
        if choice == "4":
            break
        if choice == "3":
            print(report())
        elif choice in ("1", "2"):
            name = input("Tool name: ").strip().lower()
            quantity = input("How many? ").strip()
            if not quantity.isdigit():
                print("Please enter a whole number.")
                continue
            quantity = int(quantity)
            if choice == "1":
                total = add(name, quantity)
                print(f"Now holding {total} {name}.")
            elif lend(name, quantity):
                print(f"Lent {quantity} {name}.")
            else:
                print(f"Can't lend {quantity} {name}.")
        else:
            print("That isn't an option.")
    print("Goodbye.")


if __name__ == "__main__":
    main()

shelf.py
keeps and changes the shelf

shelf = {"ladder": 1, "drill": 2, "sander": 0}


def add(name, quantity):
    shelf[name] = shelf.get(name, 0) + quantity
    return shelf[name]


def lend(name, quantity):
    if name not in shelf:
        return False
    if shelf[name] < quantity:
        return False
    shelf[name] -= quantity
    return True


def report():
    lines = []
    for name, quantity in sorted(shelf.items()):
        marker = "" if quantity > 0 else " (all lent out)"
        lines.append(f"{name}: {quantity}{marker}")
    return "\n".join(lines)

Each click shows the next step of the trace. The path starts in main(), crosses into shelf.py, and comes back.

That is one complete path through Lend-a-Hand, and it answers the bug report. lend returned False because shelf["sander"] holds 0: every sander the library owns is already lent out. The message Can't lend 1 sander. is true, and it never says which of the two guard clauses in lend stopped it. Every other path through this program is shorter than the sander path, or reuses pieces of it.

6. Step 5: predict, then run

For each function, write down what you think it returns for one specific input before you study the body. Then check it. Read the body line by line, or open the REPL in the folder and call the function yourself.

A prediction you get wrong is the most useful thing step 5 produces. It marks one exact spot where your model of the program and the program disagree, and it tells you which of the two to go fix: your model, not the code. That is a finding, and findings get written down. A round of step 5 where every prediction is right has taught you nothing you did not already believe.

A volunteer buys three mowers, and shelf has no mower key yet. What does add("mower", 3) return?

Need a hint?

add has two lines. The first one stores a value in the dictionary. Read the second line, and ask what expression sits after the word return.

The 0 in shelf.get(name, 0) is the author's second note to you. It is a default, handed back when the key is missing. Take the default out so the line reads shelf[name] = shelf.get(name) + quantity, then add a tool the shelf has never held, and Python stops with this:

Traceback (most recent call last):
  File "try_add.py", line 3, in <module>
    add("mower", 3)
    ~~~^^^^^^^^^^^^
  File "shelf.py", line 5, in add
    shelf[name] = shelf.get(name) + quantity
                  ~~~~~~~~~~~~~~~~^~~~~~~~~~
TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'

.get with no default hands back None for a missing key, and None + 3 is not an addition Python can do. So that 0 is the whole reason a volunteer can add a tool the library has never owned before. The author put it there on purpose, and now you can say why.

A wrong prediction is a finding

Here is a prediction worth getting wrong. You choose 2 to lend, type drill, and then type two where Lend-a-Hand wants a number. It answers Please enter a whole number. You then type 7. What does Lend-a-Hand do with the 7?

Here is the real session, start to finish:

Lend-a-Hand: the tool shelf.

1. Add  2. Lend  3. Report  4. Quit
Choose (1-4): 2
Tool name: drill
How many? two
Please enter a whole number.

1. Add  2. Lend  3. Report  4. Quit
Choose (1-4): 7
That isn't an option.

1. Add  2. Lend  3. Report  4. Quit
Choose (1-4): 4
Goodbye.

If you predicted that the 7 would be taken as the quantity, you did not fail the question. You found something, and this is the kind of thing step 5 exists to surface. Your model of the program said "ask again for the one value that was wrong." Lend-a-Hand does "start the whole action over," because continue jumps to the top of the while loop and the first thing that loop does is print the menu.

Write the difference down in plain words: "Typing a word at the quantity question sends the volunteer back to the menu, not back to the quantity question." Whether the author meant it to work that way is a fair question, and neither file answers it. That one belongs in the "guessing" column.

7. Reading code a model wrote

An AI model will write code like Lend-a-Hand for you, faster, with tidier comments, and in a tone of complete confidence. Reading it is the same six steps with one adjustment: the confidence tells you nothing. Generated code is plausible, and plausible is not the same as correct, so the suspicion has to come from you.

Here is a function a model produced when it was asked for a piece of a shopping program.

def total_price(prices):
    total = 0
    for price in prices:
        total = price
    return total

print(total_price([1.50, 4.00, 3.50]))

Predict first, then read the loop body closely. What does this program print?

The name total_price and the line total = 0 are both notes about intent: this function is meant to add things up. The body does not add anything up. When a name and a body disagree, you have found the bug, and the name usually tells you which of the two to change.

Now say it the way a good bug report says it. "total_price([1.50, 4.00, 3.50]) returns 3.5. Expected 9.0. The loop assigns instead of adding, on the line total = price." Concrete input, actual output, expected output, and where. That one sentence is worth far more than "it's broken," and it is the sentence you will be asked to write for the rest of the year.

8. Step 6: what you know and what you are guessing

Step 6 is two lists on one page. Move an item from "guessing" to "know" only after you have run code that settles it. Whatever is still in the "guessing" column at the end is your list of questions, and it is a much better list than the one you could have written before you started. Here are the two lists for Lend-a-Hand.

Know: one dictionary of tool counts lives in shelf.py. add can create a tool the shelf never held, because .get(name, 0) supplies a starting count of zero. lend refuses a tool that is not a key, and refuses a quantity larger than the count. report returns the list alphabetically as one string, and main.py is what prints it. Typing a word where a number belongs sends the volunteer back to the menu.

Still guessing: whether the author meant continue to go all the way back to the menu. Whether the shelf is supposed to remember its counts after you quit, which it does not, since shelf is rebuilt from that first line on every run.

Try it. The six steps are out of order. Click them in the order the method runs them.

  • Find the data: the one thing the program remembers, and its shape.
  • Write down what you know and what you are guessing, in two lists.
  • Run it with good input and bad input.
  • Predict what one function returns, then run it and compare.
  • Find the entry point and map the files by their import and def lines.
  • Trace one action from input to output, through every function it touches.
Need a hint?

Two of the six are pinned by what they need. You cannot trace an action until you know which file starts the program, and you cannot write an honest "know" list until the running and predicting have given you something to put in it.

9. Summary and reflection

Run the program before you read it, so you have facts to check your reading against. Find the entry point and the one piece of data everything revolves around, then trace a single action all the way from input to output. Predict what a function returns before you study it, and treat a wrong prediction as a finding about your own model rather than a mistake. Keep the two lists, and move an item across only after running code.
