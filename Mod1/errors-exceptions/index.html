The Exception Nobody Caught

~14 minutes Interactive No setup needed to read

1. The update that took down half the internet

On May 29, 2025, Google engineers shipped a new quota-policy feature inside Service Control with no error handling around it, and no feature flag (a switch to quickly turn it off if something went wrong) — so it went live everywhere at once, untested against real conditions.

Two weeks later, a policy change with unexpectedly blank fields synced to every data center worldwide. The moment Service Control read it, the new code hit a value that wasn't there and raised a null pointer exception — the error you get when code tries to use something that doesn't exist. Nothing was watching for that failure. Every Service Control process that read the bad policy crashed, then crashed again on restart, everywhere, at once. For roughly three hours, no request anywhere could be authenticated, checked, or logged, taking down Gmail, Google Workspace, and countless other apps built on Google Cloud with it.

Source: Google Cloud's own incident report on the June 12, 2025 outage, published at status.cloud.google.com/incidents/ow5i3PPK96RduMcb1SsW.

None of that ran in Python, but strip away the data centers and the shape is one a beginner can reproduce in ten lines: code that assumes its input looks a certain way, meets input that doesn't, and has nothing standing between that surprise and a crash. This reading builds a smaller version — a script processing signup forms, one with a bad value — and shows the one habit that would have stopped it.

3. Catching one specific problem, on purpose

Here's the smaller, Python-shaped version. This function turns a batch of signup forms into a list of valid ages:

def process_signups(forms): valid_ages = [] for form in forms: age = int(form["age"]) valid_ages.append(age) return valid_ages

Feed it five clean forms and it works. Feed it one where an age is "twenty-five" instead of "25", and int("twenty-five") raises a ValueError. Nothing catches it — the exception propagates up, the function stops, and the loop stops with it. The rest of the batch never gets its turn, because one bad row crashed everything on its way past.

The fix wraps a try/except around just the line that can fail, naming the exact exception to catch:

def process_signups(forms): valid_ages = [] for form in forms: try: age = int(form["age"]) valid_ages.append(age) except ValueError: print(f"Skipping row: age {form['age']!r} is not a number") return valid_ages

Python runs try first. If int(form["age"]) succeeds, except never runs. If it raises ValueError, Python jumps to except, runs it, and continues with the next form. One bad row gets logged and skipped; the rest finishes.

It's tempting to just write except: and catch everything. That's a real anti-pattern, worse than it looks: a bare except: also catches a typo like form["agee"] (a KeyError), a failed network call, or any unrelated bug — all swallowed silently. That's not resilience, it's a program lying about how well it's working. Naming the exact exception means real bugs still crash loud enough to notice, while the one failure you planned for gets handled gracefully.

7. Summary & reflection

A try/except block that names one specific exception type lets a program recover from the one failure you actually planned for, and keeps running instead of stopping cold. A bare except: looks like the same safety net, but it silently catches everything, including the bugs you'd actually want to know about. Google's own three-hour, worldwide outage traced back to a code path with no error handling wrapped around it at all. Naming the exception you expect is the habit that keeps a Python script's version of that failure small, visible, and survivable.
