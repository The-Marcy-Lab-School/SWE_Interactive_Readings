The Exception Nobody Caught

~14 minutes Interactive No setup needed to read

1. The update that took down half the internet

On May 29, 2025, engineers at Google shipped a new quota-policy feature inside Service Control. The new code path had no error handling wrapped around it, and it wasn't protected behind a feature flag (a switch that would have let a team turn the new path off instantly if it misbehaved) — so it went live everywhere at once, even though nothing had actually exercised it yet.

Two weeks later, on June 12 at about 10:45 a.m. Pacific time, someone pushed a policy change into Spanner, Google's globally distributed database that keeps configuration data synced across every data center within seconds. That change contained fields that were unexpectedly blank. The moment Service Control tried to read the policy, it hit the new code path, tried to use a value that wasn't there, and hit a null pointer exception: the error you get when code tries to use something that doesn't exist. Nothing in that code path was watching for that specific failure, so nothing caught it. Every Service Control process that read the bad policy crashed outright, and each one immediately reprocessed the same bad data on restart and crashed again, in every region, worldwide, at once.

For roughly three hours, from 10:49 a.m. to 1:49 p.m. Pacific time, that crash loop meant Service Control could not do its job anywhere: no request could be authenticated, checked against quota, or logged. Every product depending on it failed alongside it, from Gmail and Google Workspace to countless companies' own apps built on top of Google Cloud.

Source: Google Cloud's own incident report on the June 12, 2025 outage, published at status.cloud.google.com/incidents/ow5i3PPK96RduMcb1SsW.

None of that ran in Python, and the exact error name (a null pointer exception) belongs to whatever language Service Control is written in. But strip away the data centers, and the shape of the bug is one a Python beginner can reproduce in ten lines: a piece of code that assumes its input will always look a certain way, meets input that doesn't, and has nothing standing between that surprise and a crash. This reading builds a much smaller version of the same shape, a script that processes a batch of signup forms where one form has a bad value, and shows the one habit that would have stopped the small version cold.

3. Catching one specific problem, on purpose

Here's the smaller, Python-shaped version of the same bug. This function is supposed to turn a batch of signup forms into a list of valid ages:

def process_signups(forms): valid_ages = [] for form in forms: age = int(form["age"]) valid_ages.append(age) return valid_ages

Feed it five forms where every age is a clean digit string, and it works exactly as written. Feed it five forms where one age is "twenty-five" instead of "25", and int("twenty-five") raises a ValueError. Nothing here is set up to catch that. The exception has nowhere to go, so it propagates all the way up, the function stops, and the loop stops with it. The forms that hadn't been processed yet never get their turn, not because anything was wrong with them, but because one unrelated row crashed the whole batch on its way past.

The fix is a try/except block wrapped around just the line that can fail, naming the exact exception type to catch:

def process_signups(forms): valid_ages = [] for form in forms: try: age = int(form["age"]) valid_ages.append(age) except ValueError: print(f"Skipping row: age {form['age']!r} is not a number") return valid_ages

Python runs the try block first. If int(form["age"]) succeeds, the except block never runs at all, it's there for one specific failure and stays out of the way otherwise. If it raises a ValueError, Python jumps straight to the except block, runs it, and keeps going with the next form in the loop. One bad row gets logged and skipped. The rest of the batch finishes.

It would be tempting to skip naming ValueError at all and just write except: by itself, catching everything. That's a real, well-known anti-pattern, and it's worse than it looks. A bare except: doesn't just catch the bad age you expected. It also catches a typo in your own code, like form["agee"] instead of form["age"], which would raise a KeyError, or a network call that failed for a reason you never anticipated, or any other bug entirely unrelated to bad user input. All of it gets swallowed the same way, silently, and the loop just keeps going as if nothing happened. That's not resilience, it's a program lying to you about how well it's working. Naming the exact exception you expect means real bugs still crash loudly enough that someone notices and fixes them, while the one failure you planned for gets handled gracefully.

6. Summary & reflection

A try/except block that names one specific exception type lets a program recover from the one failure you actually planned for, and keeps running instead of stopping cold. A bare except: looks like the same safety net, but it silently catches everything, including the bugs you'd actually want to know about. Google's own three-hour, worldwide outage traced back to a code path with no error handling wrapped around it at all. Naming the exception you expect is the habit that keeps a Python script's version of that failure small, visible, and survivable.
