Off By One Song

~14 minutes Interactive No setup needed to read

1. The bug: "skip to 3" played song 4

QueueUp is a small app a coffee shop uses to run its lounge playlist. Customers pick songs, and the app plays them in order. Here is the queue sitting behind QueueUp's bug report, written in Python:

queue = ["Skyline Drive", "Paper Boats", "Neon Static", "Better Days", "Midnight Coast"]

Square brackets create a list: an ordered collection of values, separated by commas. Order is part of what a list stores, so queue remembers that "Skyline Drive" comes before "Paper Boats". Python also gives every value in a list a numbered position, called an index.

QueueUp's "skip to song" button asked for the 3rd song and played the 4th. Whoever wrote it counted the way people count out loud, first, second, third, and wrote queue[3] for "the 3rd song". Python starts counting at 0 instead of 1. queue[0] is the first song, queue[1] is the second, and queue[2] is the third, which leaves queue[3] pointing at the fourth song, "Better Days". Every listener who asked for song 3 heard song 4, and nobody on the team noticed until a regular in the lounge asked out loud why the app kept skipping ahead.

Every box in that row has two valid addresses. Counting from the front, "Neon Static" is queue[2]. Counting from the back, the same song is queue[-3]. A negative index always counts from the end of the list, so queue[-1] is the last song no matter how long the list gets.

3. Reading a list without changing it

QueueUp's screen needs more than one song at a time. It shows how many songs are waiting, which song is up last, the next couple of titles, and whether a request is already in the queue. Every one of those reads the list and leaves it alone:

The code

print(len(queue))
print(queue[0])
print(queue[-1])
print(queue[1:3])
print("Neon Static" in queue)
print("Clair de Lune" in queue)

What it prints

5
Skyline Drive
Midnight Coast
['Paper Boats', 'Neon Static']
True
False

Four different reads, four rules:

  • len(queue) gives the number of values in the list, which is 5 here. The last index is always one less than the length, so the last song is queue[4].
  • queue[-1] counts from the end, so it reaches the last song without anyone working out the length first.
  • A slice queue[1:3] builds a brand new list from the values at index 1 up to but not including index 3. That is why two songs come back, not three.
  • "Neon Static" in queue asks whether that exact value sits somewhere in the list, and gives back True or False. It never gives back a position.

QueueUp's buggy line was written as queue[3], meaning "the 3rd song". Which song does queue[3] actually return?

Need a hint?

Count from 0, not 1: queue[0] is the 1st song, queue[1] is the 2nd, queue[2] is the 3rd. Keep counting up by one to find what queue[3] lands on.

Visiting every song

Printing the whole queue, one song per line, is the most common thing anyone does with a list. A for loop visits each value in order:

The code

for song in queue:
    print(song)

What it prints

Skyline Drive
Paper Boats
Neon Static
Better Days
Midnight Coast

for song in queue assigns one value to song on each pass, with no index and no range() anywhere. When the position matters too, enumerate() hands over both:

The code

for position, song in enumerate(queue):
    print(f"{position + 1}. {song}")

What it prints

1. Skyline Drive
2. Paper Boats
3. Neon Static
4. Better Days
5. Midnight Coast

enumerate() produces a position and a value on each pass, and the position starts at 0 like every other index. QueueUp adds 1 before printing, so the screen reads "1." beside the first song. That is the same gap between everyday counting and Python counting that broke the skip button, handled on purpose this time.

4. Changing a list in place

Listeners keep adding songs, pulling songs, and fixing typos in titles, so QueueUp has to change the queue while the app runs. Strings do not allow that. A string method such as upper() builds a new string and leaves the original alone, and assigning to one character raises an error. Lists do allow it. Here are both, side by side:

A string, which cannot change

name = "ben"
name[0] = "J"

It raised:

TypeError: 'str' object does not
support item assignment

A list, which can change

end = ["x", "y", "z"]
end[1] = "foo"
print(end)

It printed:

['x', 'foo', 'z']

Lists are mutable: Python can change the values inside a list that already exists. Notice that end is never reassigned. The variable still refers to the same list, and only the contents of that list moved. Strings, numbers, booleans, and None are immutable. Lists and dictionaries are mutable.

Six operations cover almost everything QueueUp does to the queue:

  • queue.append(value) adds the value to the end, making the list one longer.
  • queue.insert(index, value) puts the value at that index and pushes everything after it one place to the right.
  • queue[index] = value replaces the value at that index. The length does not change.
  • queue.remove(value) removes the first value equal to the one given.
  • queue.pop() removes the last value and hands it back. queue.pop(index) removes the value at that index instead.
  • del queue[index] removes the value at that index. del is a statement rather than a method, so it has no dot and no parentheses.

Running all six in a row on a short queue shows what each one leaves behind:

queue = ["Paper Boats", "Neon Static", "Better Days"]

queue.append("Ocean Drive")
queue.insert(0, "Skyline Drive")
queue[2] = "Neon Static (live)"
queue.remove("Better Days")
queue.pop()
del queue[0]

Predict the list after each operation before you click. Each click runs the next line and adds the resulting list to the panel.

After those six lines, queue holds ['Paper Boats', 'Neon Static (live)']. One more line runs: queue.insert(1, "Ocean Drive"). What does queue hold then?

A list can hold other lists

QueueUp groups the evening into sets, and each set is itself a list of songs. A list is allowed to hold lists, and a list of lists is called a 2D list:

The code

sets = [
    ["Paper Boats", "Neon Static"],
    ["Better Days", "Ocean Drive"],
]

print(sets[0])
print(sets[1][0])
print(len(sets))

What it prints

['Paper Boats', 'Neon Static']
Better Days
2

The first index picks the row and the second index picks the position inside that row, so sets[1][0] reads as "row 1, then position 0 of that row". len(sets) counts the rows, which is 2, not the four songs spread across them.

5. Two names, one list

QueueUp shipped a "preview the shuffle" button. It was meant to show what a shuffled set would look like without touching the live queue. The developer wrote preview = queue, shuffled preview, and the live queue came out shuffled too. The assignment never made a copy.

Here is the rule behind that. Every value in Python is an object that lives somewhere in memory, and a variable is a name that refers to one of those objects. A list works that way, and so does a number. The id() function gives the number that identifies the object a name refers to, and is asks whether two names refer to the very same object:

The code

nums = [1, 2, 3]
clone = nums
print(nums is clone)

x = 5
y = x
print(x is y)

What it prints

True
True

clone = nums does not build a second list. It gives one list a second name, and nums is clone reports True because both names refer to the same object. The same is true of x and y, which both name the number 5. A name in Python is a reference to an object, and that holds for every type.

What separates a list from a number is whether the object itself can change. A list is mutable, so Python can change the values inside it. A number is immutable, and no operation in Python turns the number 5 into the number 6. Watch what that does to two pairs of names:

Changing a value inside the list

nums = [1, 2, 3]
clone = nums
clone[1] = 20

print(nums)
print(clone)

It printed:

[1, 20, 3]
[1, 20, 3]

Pointing a name at a new number

x = 5
y = x
y = 6

print(x)
print(y)

It printed:

5
6

clone[1] = 20 reaches inside the one list both names refer to and swaps a value, so nums and clone both print [1, 20, 3]. y = 6 cannot reach inside the number 5 and edit it, so it does the only thing left: it points y at a different object, and x keeps the 5 it already had. Python does not store lists and numbers in two different ways. It is mutability, and only mutability, that decides whether a change made through one name shows up through another.

QueueUp's preview bug, in four lines.

up_next = ["Paper Boats", "Neon Static"]
preview = up_next
preview.append("Ocean Drive")

print(len(up_next))

What number does print(len(up_next)) show?

Need a hint?

preview = up_next gives one list a second name. Ask yourself which list preview.append("Ocean Drive") grows, and then how many values that list holds.

6. A function that changed the caller's queue

QueueUp's "now playing" panel calls play_next to move on to the next song. The function takes the queue and pops the first song off it:

def play_next(songs):
    songs.pop(0)

up_next = ["Paper Boats", "Neon Static", "Better Days"]
play_next(up_next)

print(up_next)

It printed:

['Neon Static', 'Better Days']

The caller handed over its queue and got back a queue one song shorter. A parameter receives a reference to the caller's list, so songs inside play_next and up_next outside it are two names for one list. songs.pop(0) changes that one list, and the caller sees every bit of the change.

The line that shortened the list sits inside play_next. When the short queue causes trouble later, on the screen or in some other function, the line where the trouble appears is nowhere near the line that caused it. That distance is what makes this kind of bug slow to track down.

A pure function cannot surprise a caller this way. A pure function has two properties:

  1. It returns the same output every time it is given the same input.
  2. It has no side effects, which means nothing outside the function changes because the function ran.

A function that breaks either one of those is impure. play_next mutates the caller's list, so play_next is impure.

Copying the list first is the fix. These three lines all build a new list holding the same values, and any of them works:

copy1 = list(songs)   # list() builds a new list from any sequence
copy2 = songs[:]      # a slice with no start and no end copies the whole thing
copy3 = [*songs]      # the * unpacks the values into a new list literal

Here is rest_of_set, which does the same job as play_next and copies first:

def rest_of_set(songs):
    remaining = list(songs)
    remaining.pop(0)
    return remaining

up_next = ["Paper Boats", "Neon Static", "Better Days"]
later = rest_of_set(up_next)

print(up_next)
print(later)

It printed:

['Paper Boats', 'Neon Static', 'Better Days']
['Neon Static', 'Better Days']

list(songs) builds a new list, so remaining.pop(0) shortens that new list and leaves the caller's list at its full three songs. rest_of_set speaks to its caller only through the value it returns, which is what makes it pure. Side by side, the copy is the whole difference between the two function bodies:

Impure
play_next pops the caller's list

def play_next(songs):
    songs.pop(0)

Pure
rest_of_set pops a copy

def rest_of_set(songs):
    remaining = list(songs)
    remaining.pop(0)
    return remaining

7. Summary and reflection

A list keeps values in order, and every value has an index counted from the front starting at 0, or from the back starting at -1. len(), slicing, in, for, and enumerate() all read a list without changing it. append, insert, bracket assignment, remove, pop, and del change a list in place, because lists are mutable. A variable holds a reference to a list rather than the list itself, so two names can refer to one list and a change made through either name shows up through both. A function given a list receives that same reference, which is why a function can shorten, empty, or reorder the caller's list. Copying the list first keeps the function pure.
