Zero Is Not Nothing

~14 minutes Interactive No setup needed to read

1. A week that looked like missing data

Ledger Lite is a simulated budgeting app that shows a student one line a week: how much money they spent. During its first week of testing, a student who spent nothing at all opened the app and read "We couldn't find your spending data." The student emailed support to ask whether the app had lost a week of records. The app did not lose any data. The student simply hadn't spent anything that week, so the total was 0.

Here is the function that produced that message:

def weekly_summary(total):
    if not total:
        return "We couldn't find your spending data."
    return f"You spent ${total} this week."

Read if not total: out loud and it sounds like "if there is no total." Python reads that line as "if total is zero, empty, or missing," because an if statement first converts the value it is given into True or False. A total of 0 converts to False, which is how a week of spending nothing produced a missing-data message. The next few sections cover that conversion and the rule Python uses to decide which line runs next.

3. Control flow, and why the order of the conditions matters

Spending $250 in a week and spending $20 should not get the same output from Ledger Lite, and a program that runs every one of its lines every time cannot tell those two weeks apart. Python runs statements from top to bottom by default, and that order is called control flow. An if / elif / else chain changes that order: Python tests each condition from the top, runs the first branch whose condition is True, and skips the rest of the chain.

Ledger Lite uses a chain to label how a week went:

def spending_tier(total):
    if total > 200:
        return "Over budget"
    elif total > 100:
        return "Getting close"
    else:
        return "On track"

Python evaluates an elif only when every condition before it in the chain tested False. That rule makes the order of the conditions part of the logic rather than a style choice. A developer who rearranges the chain to read "smallest first" writes this instead:

def spending_tier(total):
    if total > 100:
        return "Getting close"
    elif total > 200:
        return "Over budget"
    else:
        return "On track"

Trace $250 through that version. Python tests total > 100 first. 250 is greater than 100, so that branch returns "Getting close" and the chain ends before elif total > 200: is ever evaluated. Trace $120 and the same first condition is True again, so it returns "Getting close" too. Both students read the exact same label. The student who spent $250 has already crossed the $200 line the app was built to warn about, and "Getting close" tells that student the opposite: still under the line, with room left to spend. Need a hint?

Start at the top of the chain and test the conditions in the order they are written. Stop at the first one that is True, because Python stops there too.

When the elifs become separate if statements

The order of conditions matters: if you put the conditions in the wrong order, Ledger Lite shows one label from the wrong tier. A second mistake, deleting the el from each elif, shows several labels at once, and it is harder to spot. Picture a developer tidying up spending_tier who deletes those two letters from every elif and changes nothing else. Every line still reads like a sensible condition, so nothing in the code looks broken.

Here is the original spending_tier chain together with the tidied-up version, which is named label_week. label_week prints instead of returning, so every line that runs stays visible:

The spending_tier chain
one if, then elif, then else

def spending_tier(total):
    if total > 200:
        return "Over budget"
    elif total > 100:
        return "Getting close"
    else:
        return "On track"

The label_week version
four separate if statements

def label_week(total):
    if total > 100:
        print("Getting close")
    if total > 200:
        print("Over budget")
    if total > 500:
        print("Way over")
    if total <= 100:
        print("On track")

label_week(250)

Each elif in the spending_tier chain is attached to the if that opens the chain, so Python evaluates an elif only when every condition before it in that chain tested False. Each if in the label_week version is attached to nothing. Python evaluates all four of those conditions, top to bottom, and runs the body of each one that is True. So spending_tier runs at most one branch per call, and label_week can run several.

Check every line that label_week(250) prints. More than one is possible.

Need a hint?

There is no elif in label_week, so nothing earlier in the function can stop Python from evaluating a given if. Test all four conditions against 250 separately and check off every one that comes out True.

4. Boolean context: what an if does to the value you give it

An if statement does not require a boolean. It creates a boolean context, which means Python first converts whatever value follows if into True or False by calling the bool() function on it.

bool() follows a single rule. All values are truthy except for None, False, the numbers 0 and 0.0, the empty string "", and empty collections such as [] and {}. Those are the falsy values. Everything else Python can hold is truthy.

print(bool(0))        # False
print(bool(""))       # False
print(bool(None))     # False
print(bool([]))       # False  (an empty list)
print(bool(100))      # True
print(bool("hello"))  # True

That rule explains the bug from the start of this reading. The student spent nothing all week, so weekly_summary received total = 0. The if not total: line put 0 in a boolean context, and bool(0) produced False. The not operator flips a boolean to its opposite, so not False produced True and the return on the next line ran. weekly_summary never asked whether the data existed. It asked whether total was falsy, and 0 and None are both falsy, so the function could not tell a $0 week apart from a week with no data at all.

Check every value below that Python treats as falsy. Each one is written the way Python writes it, and more than one of them is falsy.

Need a hint?

Every falsy value is a "nothing" of some kind: no value, no quantity, no characters, no items. Two of the eight are not a nothing of any kind: one is a string that holds a character, and one is a number that is not zero.

Predict before you read on. This snippet catches almost everybody the first time:

if "False":
    print("printed")
else:
    print("skipped")

What does that snippet print?

if not total: was the wrong question for Ledger Lite, but it is the right question most of the time. Any function handed something a person may have left empty has to decide first whether there is anything to work with at all:

def greet(name):
    if not name:
        return "I can't say hi if I don't know your name!"
    return f"Hi, {name}! Nice to meet you."

print(greet(""))      # I can't say hi if I don't know your name!
print(greet("Jane"))  # Hi, Jane! Nice to meet you.

The empty string is falsy, so bool("") is False and not "" is True, and the first return runs. "Jane" is a non-empty string, so it is truthy. not "Jane" evaluates to False, and Python skips past the guard to the greeting line. You will see if not something: in nearly every program that takes input.

if not value: cannot tell None apart from 0 or "", because bool() answers False for all three. Ledger Lite needed exactly that difference. When the question really is "is this None?", write if value is None:, which compares the value against None itself instead of converting it to a boolean:

def weekly_summary(total):
    if total is None:
        return "We couldn't find your spending data."
    return f"You spent ${total} this week."

0 is not None, so the first return is skipped and the student who spent nothing reads "You spent $0 this week."

5. Guard clauses: handling the exceptions first

Ledger Lite's summary has three things to rule out before it can print a dollar amount. Nobody may be logged in, the week's total may never have been recorded, and the total may come back negative, which happens when a refund gets counted twice. Nested if statements can rule out all three, and each if pushes the real work one more level to the right:

def weekly_summary(user, total):
    if user is not None:
        if total is not None:
            if total >= 0:
                return f"You spent ${total} this week."
            else:
                return "That total looks wrong. We're checking it."
        else:
            return "We couldn't find your spending data."
    else:
        return "Please log in to see your summary."

The line that does the actual job sits four levels in. To know when that line runs, a reader has to hold three separate conditions in mind at the same time, and each else sits far below the if it belongs to. A reader who loses track of one condition will believe the function returns a dollar amount in a case where it really returns an error message.

A guard clause is a single if statement that returns early. A return ends the function the moment it runs, so once a guard returns, Python never evaluates another line of that function. Each guard handles one exceptional case and returns, so the lines that follow it can assume that case is already ruled out. That is what keeps the main path at a single indentation level:

def weekly_summary(user, total):
    if user is None:
        return "Please log in to see your summary."
    if total is None:
        return "We couldn't find your spending data."
    if total < 0:
        return "That total looks wrong. We're checking it."
    return f"You spent ${total} this week."

Guard order matters for the same reason the order of an elif chain matters: the first guard whose condition is True returns, and the guards after it never run. Write the narrowest condition first.

The last return needs no if of its own. If the program reaches that line, all three guards tested False, which tells you user exists, total exists, and total is zero or more. Those are exactly the conditions the normal case requires, so there is nothing left for a condition on that line to test. The diagram below shows what the guards do to the shape of the function.

Need a hint?

Two things pin the order down. Comparing None to a number with > raises an error, so the guard that catches None has to run before any comparison does. The narrowest-first rule from section 5 still applies too: the first guard that is True returns, so a wider condition placed above a narrower one returns first and the narrower one never runs.

6. Conditional expressions: choosing a value on one line

Ledger Lite's summary line has to say "1 purchase" or "3 purchases". Both branches of a full if / else statement assign to the same variable, word, so a reader has to get through four lines to learn that the only thing changing is one string:

# Okay - an if statement picks which block of code runs
if count == 1:
    word = "purchase"
else:
    word = "purchases"

# Better - a conditional expression picks which value gets assigned
word = "purchase" if count == 1 else "purchases"

The form is value_a if condition else value_b, and the whole expression becomes value_a when the condition is True and value_b when it is False. A conditional expression produces a value and nothing else, so use one when both branches assign to the same variable, and keep the full if / else statement when the two branches need to run different code.

7. Summary and reflection

An if / elif / else chain runs the first branch whose condition is True and skips the rest, so the order you write the conditions in decides which label a value gets. Turn those elif statements into separate if statements and Python evaluates every one of them, so several branches can run on a single call. An if also converts the value you hand it with bool(), which is why 0 and "no data" look identical to if not total:.
