The Traceback Nobody Read to the Bottom

~20 minutes Interactive No setup needed to read

1. A crash report read from the wrong end

Tally is a simulated app that a food-pantry volunteer team uses to count how many meal boxes each shift packed. One Saturday it crashed on the first volunteer who typed a number into it, and it kept crashing all morning.

Python printed an eleven-line crash report. The volunteer handling support read the first few lines. Those lines named main.py, line 7, so the morning went into rewriting main.py. Tally kept crashing.

The last four lines of that same report named a different file, counts.py, line 2, and said in plain words what had gone wrong there. Nobody read that far.

Python prints a crash report oldest call first and most recent call last. The line where the error actually happened sits at the bottom, and so do the error's name and message. Start at the top instead and you get the call that kicked everything off, which is almost never where the fix goes. This reading covers how to tell Python's two kinds of error apart, how to read a crash report from the bottom up, and how to catch an error on purpose instead of letting it stop the program.

3. Did any of the program run?

Python has two kinds of error, and one question tells them apart: did any of the program run before the error appeared?

Python reads and checks a whole file before it runs any of it. A syntax error means the file is not valid Python, so Python rejects the file and line 1 never runs. A runtime error works differently. The file is valid, Python starts running it, and the error appears only once the program reaches the broken line. Every line before that one has already run.

Here are two versions of Tally's startup file. broken.py is missing a closing quote mark on line 3. startup.py is valid Python that asks int() to turn the word none into a number.

broken.py
a missing quote mark on line 3

print("Tally is starting up")

print("shift log for Saturday)

startup.py
valid Python, an unusable value

print("Tally is starting up")

print(int("none"))

What python3 broken.py prints:

  File "/Users/jellyspratley/tally/broken.py", line 3
    print("shift log for Saturday)
          ^
SyntaxError: unterminated string literal (detected at line 3)

What python3 startup.py prints:

Tally is starting up
Traceback (most recent call last):
  File "/Users/jellyspratley/tally/startup.py", line 3, in <module>
    print(int("none"))
          ~~~^^^^^^^^
ValueError: invalid literal for int() with base 10: 'none'

broken.py printed no greeting at all, even though its print on line 1 is perfectly good. Python never got as far as running line 1, because the file was rejected first. startup.py printed the greeting, then failed on line 3. Python calls a runtime error an exception, and exceptions are what the rest of this reading is about, because those are the ones a running program can still do something about.

You run a Python file whose first line is print("Tally is starting up"). An error appears, and Tally is starting up is nowhere in the output. Which kind of error is it?

4. Reading a traceback from the bottom up

Python's report for a runtime error is called a traceback. Here is the one Tally printed that Saturday. A volunteer typed 18 at the prompt, and this is the whole thing.

How many boxes did this shift pack? 18
Traceback (most recent call last):
  File "/Users/jellyspratley/tally/main.py", line 7, in <module>
    record_shift()
    ~~~~~~~~~~~~^^
  File "/Users/jellyspratley/tally/main.py", line 5, in record_shift
    print(add_boxes(120, boxes))
          ~~~~~~~~~^^^^^^^^^^^^
  File "/Users/jellyspratley/tally/counts.py", line 2, in add_boxes
    return total + boxes
           ~~~~~~^~~~~~~
TypeError: unsupported operand type(s) for +: 'int' and 'str'

The first line, Traceback (most recent call last):, states how the rest of it is ordered. Python prints the oldest call first and the most recent call last. So the call that was running at the moment the error happened is the last File line, and the error's name and message come after that, on the very last line. Reading a traceback from the bottom up is what puts those two pieces first.

Read Tally's traceback that way, one piece at a time.

  1. The error type and message. TypeError: unsupported operand type(s) for +: 'int' and 'str' is the last line. TypeError is the error's name, and the message says a + was handed an int and a str. Python will not add a number to a string.
  2. Where it happened. File ".../counts.py", line 2, in add_boxes is the last File line, so line 2 of counts.py is where Python was standing when it gave up. The two lines under that one show the code on line 2, return total + boxes, with a ^ sitting under the + that failed.
  3. The chain of calls that led there. The earlier File lines run oldest first. record_shift() ran on line 7 of main.py, which called add_boxes(120, boxes) on line 5 of main.py, which ran line 2 of counts.py.

When the traceback crosses two files

Tally is split into two files, so the chain of calls crosses files too, and the name on the File line changes partway down. The rule for reading it does not change. What changes is that the line where the error happened and the line where the bad value came from now sit in different files, and the traceback puts both line numbers in front of you.

add_boxes is not the problem. It adds two numbers, which is all it claims to do. input() always returns a string, so boxes held the string "18" rather than the number 18, and line 5 of main.py handed that string to add_boxes. The fix is int(boxes) in main.py, and nothing in counts.py needs to change. The volunteer who rewrote main.py all morning was in the right file by accident and had no way to know which line to touch, because the line number that mattered was in the part of the traceback nobody read.

Four pieces of Tally's traceback are listed in the order Python printed them. Click them in the order you should read them.

  • File ".../main.py", line 7, in <module>
  • File ".../main.py", line 5, in record_shift
  • File ".../counts.py", line 2, in add_boxes
  • TypeError: unsupported operand type(s) for +: 'int' and 'str'
Need a hint?

most recent call last is a promise about print order, so the newest piece of the story is at the end of the traceback. Start with the piece that tells you what went wrong, then the piece that tells you where, then work back through who called whom.

Tally's traceback names three lines: main.py line 7, main.py line 5, and counts.py line 2. Which one shows where the string came from?

5. Catching the error you expect

Most errors you fix by editing the program. Some you cannot, because they depend on what a person types, or on a file that may not be there, or on a network that may be down. For those you can plan ahead and catch the error. Catching it stops the program from being shut down and lets your own code decide what happens next.

Tally adds up a day's shift log in a file called shift_log.py. One Saturday a volunteer wrote none in the log instead of a number, and total_boxes had no plan for that.

total_boxes with no plan for a bad entry, and what it prints:

def total_boxes(entries):
    total = 0
    for entry in entries:
        total = total + int(entry)
    return total

print(total_boxes(["18", "24", "none", "31"]))
Traceback (most recent call last):
  File "/Users/jellyspratley/tally/shift_log.py", line 7, in <module>
    print(total_boxes(["18", "24", "none", "31"]))
          ~~~~~~~~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File "/Users/jellyspratley/tally/shift_log.py", line 4, in total_boxes
    total = total + int(entry)
                    ~~~^^^^^^^
ValueError: invalid literal for int() with base 10: 'none'

total_boxes catching ValueError, and what it prints:

def total_boxes(entries):
    total = 0
    for entry in entries:
        try:
            total = total + int(entry)
        except ValueError as err:
            print(f"Skipping an entry: {err}")
    return total

print(total_boxes(["18", "24", "none", "31"]))
Skipping an entry: invalid literal for int() with base 10: 'none'
73

The version with no plan for a bad entry printed no total at all. 31 was in the log and never got counted, because one entry Python could not convert stopped the loop, the function, and the program.

try and except change that. Code that might raise an error goes in the try block. What to do about it goes in the except block, with the name of the error type you are expecting. Python runs the try block first. If int(entry) succeeds, the except block never runs. If int(entry) raises a ValueError, Python jumps straight to the except block, runs it, and carries on with the next entry.

except ValueError as err hands you the error itself, under the name err. Printing err prints the error's own message, which is how the output names the entry that got skipped and says why. A plain except ValueError: with no as err catches the same error and throws away that message, so the log line would have to guess at what happened.

Why a bare except: is avoided

An except: with no error type after it catches every error there is, including the ones that are plain bugs in your own code. Here are two versions of total_boxes carrying the same typo, entrry where entry was meant.

The bare except: version, and what it prints:

def total_boxes(entries):
    total = 0
    for entry in entries:
        try:
            total = total + int(entrry)
        except:
            print("Skipping an entry")
    return total

print(total_boxes(["18", "24", "none", "31"]))
Skipping an entry
Skipping an entry
Skipping an entry
Skipping an entry
0

The except ValueError as err: version, and what it prints:

def total_boxes(entries):
    total = 0
    for entry in entries:
        try:
            total = total + int(entrry)
        except ValueError as err:
            print(f"Skipping an entry: {err}")
    return total

print(total_boxes(["18", "24", "none", "31"]))
Traceback (most recent call last):
  File "/Users/jellyspratley/tally/shift_log.py", line 10, in <module>
    print(total_boxes(["18", "24", "none", "31"]))
          ~~~~~~~~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File "/Users/jellyspratley/tally/shift_log.py", line 5, in total_boxes
    total = total + int(entrry)
                        ^^^^^^
NameError: name 'entrry' is not defined. Did you mean: 'entry'?

The bare except: version handed back a total of 0 and did not stop. A typo makes entrry a variable that was never assigned, so every entry raised a NameError, and the bare except: caught all four of them. Anyone reading that output would believe the shift log was empty, and nothing printed says otherwise.

The version naming ValueError stops instead, and its last line reads NameError: name 'entrry' is not defined. Did you mean: 'entry'?. That is the argument for naming the error type. The one failure you planned for gets handled, and any other failure still reports itself, with a traceback and a line number.

This version of total_boxes should catch the case where int() cannot convert an entry, print the error's own message, and keep going. Type the line that belongs on the blank.

def total_boxes(entries):
    total = 0
    for entry in entries:
        try:
            total = total + int(entry)
        ______________________
            print(f"Skipping an entry: {err}")
    return total
Need a hint?

Three parts. The keyword that opens the handler, then the name of the error type int() raises when a string will not convert, then the piece that gives the error a name so the print on the next line can use err. It ends with a colon, the same way if and def lines do.

6. Asking until the answer is a number

int() raises a ValueError on any text it cannot convert, and a person typing at a prompt can type anything at all. A try/except inside a while True loop is the usual answer: keep asking until int() succeeds. You will want this in any program that asks a person for a number.

def ask_for_number(prompt):
    while True:
        answer = input(prompt)
        try:
            return int(answer)
        except ValueError:
            print(f"Sorry, {answer} is not a whole number. Try again.")

boxes = ask_for_number("How many boxes did this shift pack? ")
print(f"Recorded {boxes} boxes.")

Here is a real run of ask_for_number, where the first answer typed was the word eighteen and the second was 18:

How many boxes did this shift pack? eighteen
Sorry, eighteen is not a whole number. Try again.
How many boxes did this shift pack? 18
Recorded 18 boxes.

A while True loop has no stopping condition of its own, so something inside it has to end it. Here the return does. The moment int(answer) succeeds, return ends the function, and ending the function ends the loop with it. When int(answer) raises a ValueError instead, Python jumps to the except block, the message prints, the loop starts over, and the prompt comes back.

Why not check the text with .isdigit() first?

.isdigit() is True only for text made entirely of digits. "5".isdigit() is True, but " 5".isdigit() (a 5 with a space in front of it) is False, and "-5".isdigit() is False too, even though int() converts both of those without complaint. Letting int() decide what int() accepts is the more accurate test. Reach for .isdigit() when you specifically want digits and nothing else.

Check every answer that makes ask_for_number return a number instead of asking again. More than one does.

Need a hint?

The question is only ever "does int() accept this text?" int() wants a whole number, and it does not mind a minus sign or spaces around the edges.

7. Raising an error on purpose, and testing for it

Sometimes your own function is the one that spots the problem. A negative box count is not something add_boxes can do anything sensible with, and returning a wrong total would push the mistake into a report somebody else reads. The raise keyword reports it on the spot instead. Here is add_boxes in counts.py with a guard added:

def add_boxes(total, boxes):
    if boxes < 0:
        raise ValueError(f"boxes cannot be negative, got {boxes}")
    return total + boxes

raise ValueError(...) stops add_boxes at that line and sends a ValueError to whoever called it, carrying a message that names the bad value. The caller can catch it with try/except or let it stop the program. Either way the failure gets reported at the line where the mistake really is. Pick the built-in error type whose meaning is closest: ValueError for a value Python's types allow but your function cannot use, TypeError for the wrong data type altogether.

An error a function raises on purpose is part of what that function does, so it gets a test like any other behavior. You already run tests with python3 -m pytest and check results with assert. pytest.raises(ErrorType) is the piece that checks for a raised error. This test file is tests/test_counts.py:

import pytest
from counts import add_boxes


def test_add_boxes():
    """add_boxes - adds this shift's boxes to the running total"""
    assert add_boxes(120, 18) == 138


def test_add_boxes_negative():
    """add_boxes - raises a ValueError when boxes is negative"""
    with pytest.raises(ValueError):
        add_boxes(120, -4)

with pytest.raises(ValueError): means the indented block has to raise a ValueError. If it does, pytest catches the error and the test passes. If it does not, the test fails. It is the same with statement that opens a file: it sets something up, runs the indented block, then checks what happened.

Delete the whole if statement from add_boxes, both the if line and the raise line under it, so that the function quietly accepts a negative count. python3 -m pytest then reports this:

test_add_boxes still passes, because add_boxes(120, 18) never reached the raise anyway: 18 is not negative. test_add_boxes_negative fails with DID NOT RAISE ValueError, which names the promise the function stopped keeping. Put the if statement back before moving on.

8. Summary and reflection

A syntax error means Python rejected the file, so none of the program ran. A runtime error means Python got as far as the broken line, so every line before it already ran. A traceback reports a runtime error oldest call first and most recent call last, which puts the error type, the message, and the line it happened on at the bottom. try with except ErrorType as err catches the one failure you expect and gives you its message, while every other failure still stops the program loudly enough to find. raise is how your own function reports a value it cannot work with, and pytest.raises is how a test checks that it does.
