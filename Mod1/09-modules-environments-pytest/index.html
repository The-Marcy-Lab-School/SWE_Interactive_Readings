The File That Ran Itself

~20 minutes Interactive No setup needed to read

1. A grocery bill that came up a dollar short

Chip In is a small Python program four roommates wrote to split a shared grocery bill. Hand it a total and a number of people, and it says what each person owes.

A $97 grocery run split four ways is $24.25 each. Chip In said $24. Four payments of $24 come to $96, so a dollar went missing on every grocery run, and nobody noticed for a month. Then one roommate wrote a second program that borrowed a function from Chip In, and the second program printed the old grocery bill the instant it started, unasked.

Neither problem is a typo you can find by staring at the file. Fixing them takes four things: splitting a program into separate files, knowing exactly what Python does when one file borrows from another, giving a project its own private place to install tools, and writing tests that check your functions so you do not have to.

3. One file doing three jobs

Chip In started as a single file doing the math, the printing, and the input collecting all at once. Separation of concerns is the habit of giving each file one job, and in Python you do it by splitting the program into modules. A module is a file containing code that other files can import and use. A module's name is its filename without the .py.

Here are the three files Chip In became. Each one has a single job.

bill.py
the math

def split_evenly(total, people):
    return total // people

display.py
the printing

def display(message):
    print(message)

main.py
collects the numbers and runs the other two

import bill
from display import display

def main():
    total = 97
    people = 4
    share = bill.split_evenly(total, people)
    display(f"Each of the {people} roommates owes ${share}.")

main()

Every name written at the top level of a file, meaning every function and every variable that is not indented inside something else, can be imported by another file. main.py uses both ways of importing. import bill brings in the whole bill module, and its names are reached with a dot, as in bill.split_evenly(total, people). from display import display brings in one specific name, which is then called on its own. Several names fit in one statement: from bill import split_evenly, add_tax.

The import to avoid

There is a third form. from bill import * imports every name in bill.py at once, so split_evenly(97, 4) works with nothing in front of it. It is the shortest to type and the one experienced Python developers avoid.

main.py is changed to use from bill import * instead of import bill. Check every statement that is true of that change.

Need a hint?

The word * means "everything". Ask what arrives that you never asked for, and what happens if one of those arriving names is a word Python already uses.

4. Importing a file runs it

Here is bill.py again, with the line its author used while writing split_evenly and never deleted. Checking a function by printing the answer and reading it is how most people start out.

# bill.py
def split_evenly(total, people):
    return total // people

print(split_evenly(97, 4))

You run python3 main.py, and the first line of main.py is import bill. What prints, and in what order?

Here is what python3 main.py actually printed:

24
Each of the 4 roommates owes $24.

Importing a file runs it, top to bottom, exactly as if you had typed python3 bill.py. When Python reaches import bill, it goes and runs all of bill.py: the def statement creates the function, and the print statement prints. Only then does Python come back to main.py and carry on. That is the second program printing the old grocery bill at startup, and it is not a bug in main.py at all.

Defining a function harms nothing, so a module of def statements is fine to import. The trouble starts when a file is both a program you run on its own and a module other files import.

What __name__ holds

Every module has a variable called __name__ that Python fills in automatically. Put print(f"my __name__ is {__name__}") at the bottom of bill.py and at the bottom of main.py, then run python3 main.py:

my __name__ is bill
Each of the 4 roommates owes $24.
my __name__ is __main__

An imported file's __name__ holds its module name, which is bill here. The file you actually ran with python3 has __name__ set to the string "__main__". One variable, two possible values, and a file can read it to tell which situation it is in.

The __main__ guard

That gives every Python program its standard ending. Wrap the part that should only happen on a direct run in if __name__ == "__main__":.

bill.py with the guard

def split_evenly(total, people):
    return total // people

if __name__ == "__main__":
    print(split_evenly(97, 4))

main.py with the guard

import bill
from display import display

def main():
    # ...

if __name__ == "__main__":
    main()

Read the guard as "if this file is the one being run, do this". python3 bill.py sets __name__ to "__main__", the condition is true, and the quick check prints. python3 main.py imports bill, which sets bill's __name__ to "bill", the condition is false, and nothing happens but the def. Put this guard at the bottom of every program you write. The two underscores on each side of name and main are part of the spelling, and Python uses that pattern for names it manages itself.

The first time Python imports bill.py, a folder called __pycache__ appears next to it holding bill.cpython-313.pyc, a pre-processed copy that makes the next import faster. Python rebuilds it on its own, you never edit it, and it never belongs in Git.

5. Somewhere to put pytest

Some of the code you import, you never wrote. random, math, time, and json come with Python itself. That collection is the standard library, and the habit worth building is to ask "does Python already have this?" before writing it yourself. pytest is not one of them. pytest is a package: a folder of modules somebody published so that other people can install it and import it. Third-party packages live on the Python Package Index, PyPI for short, at pypi.org, and pip is the installer that fetches them.

Installing pytest into the one Python on your computer is the thing to avoid. Different projects need different versions of the same package, so one shared pile of packages means an upgrade for one project quietly breaks another. A virtual environment is the fix: a folder inside your project holding that project's own packages, plus a link to the Python already installed on your computer. Whatever you install while it is switched on lands there and nowhere else.

python3 -m venv .venv
source .venv/bin/activate

python3 -m venv .venv means "run the venv module as a program", and .venv is the name of the folder to create. The leading dot hides it from ls so it does not clutter your view of the project. source .venv/bin/activate switches it on, and your Terminal prompt grows a (.venv) at the front, which is how you know. deactivate switches it off, and you activate again in every new Terminal window you open for this project.

pip install pytest installs five packages, not one. pytest itself needs iniconfig, packaging, pluggy, and pygments to work, so pip fetches those as well. Packages that a package needs are its sub-dependencies, and pip follows the whole chain. pytest is also a developer dependency: the people building Chip In need it, and the roommates who only run Chip In never do.

pip freeze prints every installed package with its exact version. Send that list into a file with pip freeze > requirements.txt and you have the recipe for rebuilding the environment anywhere.

iniconfig==2.3.1
packaging==26.3
pluggy==1.6.0
Pygments==2.21.0
pytest==9.1.1

The == records the exact version, so everyone who installs from this file gets the packages you tested with. requirements.txt is what you commit to Git. .venv is what you do not: it holds about 30 megabytes across roughly 2,000 files, and the programs inside it record the full path of the folder they were built in, so on a teammate's computer those paths lead nowhere. A .gitignore file lists what Git should leave alone, and both folders belong in it.

# .gitignore
.venv/
__pycache__/

Commit the recipe, not the meal. Cloning a Python project and getting it running is always these four commands, and the last one reads requirements.txt back.

cd chip-in
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

6. A test that finds the missing dollar

The only check on split_evenly so far was that print at the bottom of bill.py, and 24 looked close enough to whoever read it. Printing a result and reading it also leaves you with an awkward question once you are done: do you delete that print line, comment it out, or let it clutter bill.py? A unit test answers that. A unit test is a small program that calls one function with a known input and checks the output against what you expected, and it lives in a file of its own.

A test file is a file whose name starts with test_ and imports the functions it tests. Put test files in a tests/ folder beside the source code, and the source code stays about the product while the tests stay about the testing. Here is the whole Chip In project.

# tests/test_bill.py
from bill import split_evenly


def test_split_evenly():
    """split_evenly - splits a bill into equal shares"""
    assert split_evenly(40, 4) == 10
    assert split_evenly(97, 4) == 24.25

A test function is any function in a test file whose name starts with test_, named after the function it tests. pytest finds tests by those two name rules and nothing else, so there is nothing to configure. The string on the first line is a docstring, and in a test it says what the test checks.

assert is the whole mechanism. assert expression checks that the expression is truthy; if it is, nothing happens and the test carries on. If it is falsy, assert raises an AssertionError, the test stops, and pytest reports a failure. split_evenly(97, 4) == 24.25 is an ordinary comparison with the same == you already write. One test function can hold as many assert statements as you like, and it passes only if every one of them passes.

Run every test in the project with python3 -m pytest, from the project's root folder. The python3 -m part is what puts your project folder on the list of places Python looks for modules, so from bill import split_evenly finds bill.py. Here is the report:

tests/test_bill.py F                                                     [100%]

=================================== FAILURES ===================================
______________________________ test_split_evenly _______________________________

    def test_split_evenly():
        """split_evenly - splits a bill into equal shares"""
        assert split_evenly(40, 4) == 10
>       assert split_evenly(97, 4) == 24.25
E       assert 24 == 24.25
E        +  where 24 = split_evenly(97, 4)

tests/test_bill.py:7: AssertionError
=========================== short test summary info ============================
FAILED tests/test_bill.py::test_split_evenly - assert 24 == 24.25
============================== 1 failed in 0.02s ===============================

Three pieces of that report do the work. The F after the filename and the name under FAILURES say which test failed. The > marks the exact assert line that raised the error, so the first assert passed and the second did not. The two E lines give you the comparison that came out false and, underneath it, the call that produced the left-hand number.

Read the report, then answer. What does it tell you about split_evenly?

Need a hint?

The line where 24 = split_evenly(97, 4) is pytest showing its work. Read it as a plain sentence: the call on the right produced the number on the left.

There is the missing dollar. // divides and throws the remainder away, so 97 // 4 is 24 and the quarter disappears. Change that one character to / in bill.py and run the tests again:

tests/test_bill.py .                                                     [100%]

============================== 1 passed in 0.01s ===============================

Each dot after a filename is one passing test. python3 main.py now says Each of the 4 roommates owes $24.25., and the test stays in the project, ready to say so again every time anyone touches bill.py.

Set up Chip In yourself

This Terminal runs the real commands against a copy of the Chip In folder. Run them in order.

  1. ls — see what is in the project before you start
  2. python3 -m venv .venv — build the virtual environment
  3. source .venv/bin/activate — switch it on
  4. pip install pytest — install pytest into it
  5. pip freeze > requirements.txt — record what got installed
  6. python3 -m pytest — run the tests
What else can I try in there?

ls -a to see the dot-folders that plain ls hides, cat requirements.txt after step 5, deactivate followed by python3 -m pytest to see what a switched-off environment does, and pip install pytest before step 3 to see what happens when you install with nothing switched on.

7. Summary and reflection

Give each file one job, and import what you need by name so a reader can tell where every function came from. Importing a file runs it, so put the part that should only happen on a direct run inside if __name__ == "__main__":. Install packages into a virtual environment you create per project, record them with pip freeze > requirements.txt, and keep .venv out of Git. Write the checks you were going to print as assert statements in a test_ file, and python3 -m pytest will tell you which one failed and what the function actually returned.
