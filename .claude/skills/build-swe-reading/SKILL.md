# Build an SWE interactive reading

This is the Software Engineering Fellowship's own reading format — a **short, focused sibling** of the Data Analytics Fellowship's reading-kit pattern (same visual brand, same underlying activity primitives), but deliberately smaller in scope. Read this whole file before building or refactoring a reading. Read one already-shipped reading in this repo as a worked example before writing a new one.

## What's different from the DA fellowship's readings (don't port these over)
- **10-15 minutes total, including the video.** This is a hard ceiling, not a soft target — if the honest count (see "Time estimate" below) comes out over 15 minutes, cut an activity or trim the video pick, don't just under-report the number.
- **No recall/prerequisite-check section.** Don't open with a "test what you already know" block. Teach the topic directly.
- **No GitHub submission flow, no persona/leaderboard.** The only export/persistence story is: localStorage autosave (so a refresh doesn't lose progress) plus **"Copy Plain Text Answers"** (`ReadingKit.copyPlainText`) and **"Download as .txt"** (`ReadingKit.downloadPlainText`) buttons side by side, both producing the same title/score/free-response snapshot — one to the clipboard, one as a saved file. No GitHub issue, no alias picker.
- **Real-world use case required, and it can be a real, named public event or product**, not only a fictional-but-realistic scenario. E.g. "the CrowdStrike outage that took down Windows machines worldwide" or "GitHub's own Nov. 2024 rate-limit changes" are fair game here, as-is or lightly fictionalized. A realistic simulated scenario (invented company, real-shaped problem) is equally fine when a real citable event doesn't fit the topic. Either way the scenario must be genuinely tied to the mechanism being taught, not decorative.

## What's the same as the DA fellowship's readings (keep these)
- Same brand: `assets/brand-tokens.css` + `assets/reading-kit.css`. Never hand-pick a hex outside the token file's palette.
- Same shared engine, `assets/reading-kit.js` (a trimmed fork — see its own header comment for exactly what's missing vs. the DA kit's version). Same function names for everything it does keep: `ReadingKit.quiz()`, `.selectAll()`, `.flipCards()`, `.dragDrop()`, `.orderSteps()`, `.selfCheck()`, `.traceStepper()`, `.terminal()`, `.video()`, `.freeResponse()`, `.activity()`, `.Scoring`, `.init()`.
- Expandable hints via native `<details class="mlrk-hint"><summary>Need a hint?</summary>...</details>` — never an always-visible callout for something that's genuinely a hint.
- Expandable/revealed answers when a check makes sense (predict-then-reveal, self-check with 2 tries before showing the answer) — same 1st-try/2nd-try/reveal scoring pattern as the DA kit for quiz-shaped questions; ungraded self-checks (drag-drop, order-steps) still get 2 tries before revealing.
- Full activity variety: aim for 4-6+ different interactive types across one reading (flip cards, fill-in-the-blank/typed prediction, drag-and-drop, order-the-steps, a terminal/code simulator where the topic calls for it, select-all, single-answer quiz). Prefer typed-input activities over pure reveal-buttons where it fits.
- No module numbers, no "before lecture"/"pre-lecture"/"bridge to lecture" language anywhere in visible text — same ban as the DA fellowship, for the same reason (a reading should read as self-contained, not positioned relative to a specific class session).
- No literal or HTML-entity arrow characters (`→`, `&rarr;`, `&#8594;`, etc.) and no ASCII `->` used as narrative shorthand (e.g. "10 -> 20") — spell it out ("then", "leads to"). The one legitimate exception is a real Python return-type annotation (`def foo() -> int:`).
- WCAG AA: real alt text/`<title>`+`<desc>` on every SVG, heading hierarchy that doesn't skip levels, visible keyboard focus states, no meaning conveyed by color alone. `reading-kit.css` sets `html{font-size:125%}` (a 20px root) precisely so body text, headings, pills, and code blocks all land comfortably above a 20px-equivalent scale together, not just above some bare legal minimum — don't undo this with a page-local `font-size` override on `html`/`body`.
- **Every `<code>` term in running prose (a command, variable, path, package name) must render bold and monospace, not just as inline text.** `reading-kit.css`'s global `code{font-family:var(--mlrk-font-code);font-weight:700}` rule already does this — don't override it with a page-local `code{}` rule that drops the weight/family back to the body font. This applies retroactively too: if you see plain-looking inline code in a screenshot, the fix is almost always a conflicting local style, not a missing `<code>` tag.
- **A diagram must render centered in the page, not left-stuck with dead space beside it**, when its `max-width` is narrower than the text column. `reading-kit.css` centers `.mlrk-illustration` via `margin-left:auto;margin-right:auto`, but a reading's own page-local `.mlrk-illustration{...}` rule (every reading has one, for its own `max-width`) must set `margin-top`/`margin-bottom` **separately**, never a `margin` shorthand — a shorthand re-sets all four sides and wins over the shared rule by source order, silently re-breaking centering. Pattern to copy: `.mlrk-illustration{width:100%;max-width:700px;height:auto;margin-top:1.1rem;margin-bottom:1.1rem;display:block}`.
- **An SVG's actual rendered size is capped by whichever is smaller: its own CSS `max-width`, or the width of the column it sits in (roughly 900-920px inside `.mlrk-wrap`).** A real bug found (twice, independently) this way: raising a diagram's font-size attributes but widening the `viewBox` by the same proportion accomplishes nothing if the new viewBox is wider than the actual rendered column — the browser scales the whole SVG down to fit, and the "bigger" font shrinks right back below the intended size. Two fixes, pick whichever fits the content better: (1) keep the viewBox width close to the real column width (≈900) and stack wide content vertically instead of side-by-side, or (2) if boxes must sit side-by-side, keep the total viewBox width ≤ ~900-920 rather than scaling it up. Whichever you pick, **always verify with a real screenshot** — never assume a font-size attribute alone determines the rendered size.
- **When a diagram's caption/prose describes an arrow's direction ("points up," "runs left to right"), keep it geometrically accurate to the actual box layout, or better, don't claim a specific compass direction at all.** A real bug found this way: a diagram's boxes were arranged diagonally (parent top-left, child bottom-right), making the connecting arrow run mostly horizontal, but the caption said "points up at the parent" — wrong, and confusing to a reader looking at the actual image. The only property that's pedagogically load-bearing for a UML inheritance arrow is that the hollow triangle sits on the line and points at the parent, not which compass direction the line happens to run. Prefer wording like "sits on the line and points at X" over any specific direction.
- **When asked to cut a passage's length by some amount, actually count the words before and after** (a quick `python3 -c "print(len(text.split()))"` on the draft) rather than eyeballing whether it "feels shorter" — trust the count, not the impression, since dense/technical prose often *reads* shorter than its real word count. Preserve the concrete facts/numbers that make the scenario land (the actual date, dollar figure, percentage) even while cutting connective tissue; cut hedge words, repeated framing, and any sentence that restates a point already made rather than the facts themselves. Keep a real source citation (`<p class="mlrk-small">Source: ...</p>`) even after a heavy trim — cutting the story short is not a reason to also cut where it came from.
- **Every reading with an inline SVG diagram needs an actual headless-Chrome screenshot check, not just a source-code read.** Text overlapping a same-colored line, a text block wider than its box, and a label sitting where two diverging lines haven't yet spread apart are all real bugs that pass every other check clean and only show up by looking at the rendered page. Take a real screenshot (`google-chrome --headless --disable-gpu --no-sandbox --window-size=900,<tall> --screenshot=path.png <file-url>`; check the actual output height with `sips -g pixelHeight` or PIL before assuming a fixed height covered the whole page) and view it (crop into sections with PIL if the image is very tall). Re-screenshot after any fix to confirm it actually worked.
- Real video-duration verification before picking one — YouTube's watch page is JS-rendered, so `WebFetch` cannot see the real duration. Use:
  ```bash
  curl -s -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36" "https://www.youtube.com/watch?v=<id>" | grep -o '"lengthSeconds":"[0-9]*"' | head -1
  ```
  **A video must be under 5 minutes — hard cap, not a soft target.** A 7:28 video shipped once on the reasoning that the whole reading still fit under 15 minutes; that's the wrong test. Not every reading needs a video at all: if nothing genuinely short (under 5 min), on-topic, and from a reputable channel exists, skip the video section entirely rather than stretch the cap or force a mediocre fit. `qa/reading_qa.py` now fetches each video's real duration over the network and hard-ERRORs above 300 seconds — this is checked automatically, not just at authoring time.
- Copyright footer, same wording as the DA fellowship's: "This reading is the property of The Marcy Lab School and Angelica Spratley. Contact the owners before republishing, reusing, or monetizing this content elsewhere." (adjust the named owner only if Angelica says to).
- **When a company/product is the actual subject of the scenario (not just a passing citation), briefly say what it is/does inline, in the same sentence or the next one — don't assume the reader recognizes the name. This applies to invented/simulated names just as much as real ones.** A first real bug found this way: a reading opened with "Valve's own Steam client" and "Knight Capital Group's trading system" with no explanation of either — fine for a reader who already knows Steam is a PC game storefront or that Knight Capital was a Wall Street trading firm, useless for one who doesn't. A second round of the same bug, this time with made-up companies: "DeskBot's confirmation step," "Here's the actual queue sitting behind QueueUp's bug report," and "Here's roughly what Nimbus Rides' dispatch script looked like" all launched straight into the code with zero indication of what kind of thing DeskBot/QueueUp/Nimbus Rides even was — a made-up name carries *less* built-in context than a real company, not less need for it, since the reader can't fall back on outside knowledge at all. State what kind of thing it is in one clause the first time it's named (a help-desk chatbot, a lounge playlist app, a rideshare app), whether that name is real or invented. Universally-known real names (Amazon, Microsoft, Excel) don't need this; anything narrower does, real or invented. A source citation in a footnote-style aside is fine to leave unexplained (e.g. naming the journal or court order a fact came from) — this rule is about the company/product the scenario is actually built around.
- **The first time an acronym appears anywhere in the reading's prose (title, section 1, anywhere before the vocabulary section), spell it out inline** — e.g. "WSL (Windows Subsystem for Linux)" or "API (Application Programming Interface)" — even if that same acronym also gets its own flip card later in the vocabulary section. A real bug found this way: a reading used "WSL" four times in its opening scenario before the vocabulary section ever defined it, and a separate reading used "JSON" and "API" in its opening code example without ever spelling either one out anywhere in the file. A vocabulary flip card later in the reading does not retroactively fix an unexplained acronym earlier in the prose — the reader hits the acronym on first read, not after reaching section 2. This applies to every acronym, not just ones that end up with their own flip card; a supporting acronym that's never the actual topic (like JSON/API in a reading about dicts) still needs a one-time inline expansion, just not a full vocabulary entry.
- **An SVG tree/hierarchy diagram must show depth via each line's own `x` coordinate, never via leading whitespace inside a `<text>` element's content.** A first real bug found this way: a folder-tree diagram used `<text x="24" y="100">    └── weather-app/</text>` (four leading spaces) to indent a nested folder one level in — the leading spaces silently failed to render as visible indentation, so the nested folder looked like a sibling of its parent instead of a child. Shift `x` itself per depth level (e.g. `+34` per level) instead.
- **A long, unbroken inline `<code>` string (a full path, a long identifier) must be able to wrap inside a narrow container like a flip card.** `reading-kit.css` sets `code{overflow-wrap:break-word}` globally for exactly this — don't override it with a container that forces `white-space:nowrap` or `overflow:hidden` around code text. If you add a genuinely long code snippet anywhere narrow, sanity-check it by flipping/opening that element in a real screenshot, not just reading the source.
- **Never set `display:flex` directly on a `<label>` (or any element) that contains mixed inline content — plain text interleaved with `<code>` tags, links, etc.** A real bug found this way: `label{display:flex}` on a checklist item whose text read "...separate `if`/`elif` chain..." turned the checkbox, each text run, and each `<code>` tag into its own flex item, visually fragmenting the sentence ("i / eli", "f    f"). If a label needs `display:flex` (e.g. to align a checkbox with wrapping text), wrap everything after the input in one `<span>` so the flex container only ever has two children — `<label><input type="checkbox"> <span>text with <code>inline</code> bits</span></label>` — never flex the raw mixed children directly.
- **In an SVG diagram, never use a border/stroke tone as `<text>` fill directly on its matching light background — check WCAG contrast, don't assume the palette's existing border/fill pairing is text-safe.** A real, repo-wide bug found this way: `#C92929` (red-700) text on `#F7DFDF` (red-100) measures 4.32:1, `#83671C` (gold-700) on `#FECC5B` (gold-300) measures 3.57:1, `#2274B5` (blue-700) on `#DEEAF4` (blue-100) measures 4.06:1, and `#327A5F` (forest-600) on `#A6C2B4` (sage-300) measures 2.69:1 — all below WCAG AA's 4.5:1 minimum for normal-size text, even though every one of these is a real, intentional pairing used throughout the diagrams (border tone as both the box's stroke color and its label text color). The fix is `--mlrk-red-700-text` (`#B72525`), `--mlrk-gold-700-text` (`#675116`), `--mlrk-blue-700-text` (`#1E659D`), and `--mlrk-forest-600-text` (`#204D3C`) in `brand-tokens.css` — darkened, text-only variants of the same four tones, each verified ≥5:1 against its matching background. Use the original border tone for `stroke=` (border contrast only needs 3:1 per WCAG 1.4.11, and changing it would shift the diagram's visual identity); use the `-text` variant for any `fill=` on `<text>` that sits on that same colored background. Text sitting on the plain cream page background (outside any colored box) is unaffected — check with an actual contrast calculation, not by eye, since several of these misses are visually subtle. `qa/reading_qa.py`'s brand-color check accepts these four `-text` hexes as known-good in addition to the base palette.
- **SVG diagram label text must not run smaller than 16px.** With the page's own body text now sitting around 20px (see the root type-scale note above), a diagram using the repo's old 11-13px labels reads as noticeably, jarringly smaller than the surrounding prose — legible on close inspection, but visually "off" and the single most common source of "text is too small" feedback. `qa/reading_qa.py`'s `check_font_sizes` now WARNs on any SVG `font-size="…"` attribute under 16 (and still hard-ERRORs under 14). Bumping font size up usually means enlarging the box/viewBox to match — budget for that when redrawing, don't just increase the font-size attribute and let text spill past its container; screenshot-verify per the rule above.
- **The terminal simulator (`ReadingKit.terminal()`) provides three things automatically — don't hand-author any of them per-reading:** (1) a `placeholder="Click here to type…"` on the input, so it's visually obvious where to click before typing; (2) `(no output)` printed for any command that succeeds with an empty result (e.g. `cd`, `mkdir`, or `ls` on an empty folder) — this used to look like the simulator was broken or unresponsive, since a real bug report was exactly "ls doesn't list anything, is this expected?"; (3) a small italic caption above the input, stating plainly that there's no Tab-completion and that's intentional (it builds real typing muscle memory, not a missing feature). If you're testing a terminal activity and don't see the placeholder/hint, you're looking at a stale screenshot or an old `reading-kit.js` — these aren't something a reading's own HTML/JS needs to add.
- **Multi-step instructions ("try these commands, in order: …") must be a real `<ol>`, never a comma-separated run-on sentence.** Use the shared `.mlrk-steplist` class for consistent spacing (`<ol class="mlrk-small mlrk-steplist"><li><code>pwd</code> — confirm where you're starting from</li>...</ol>`), and let the browser's native numbering do the counting — don't also write "Step 1:" inside the `<li>` text, which double-numbers. This applies to any ordered sequence of actions a student is meant to follow, not just terminal commands (e.g. install steps, a multi-part fill-in-the-blank).
- **A quiz/predict-the-output prompt must state the setup and the question directly, not as an indirect narrative aside.** A real bug found this way: "Say you're inside `/path/to/src` — one level deeper than the terminal above ever takes you, but the same tree as the diagram in section 1. You run `cd ..`, then `ls`." buries the actual question (what does `ls` print?) inside a parenthetical qualifier about the terminal. Rewrite as two short, direct, bolded statements: "**You are currently inside `/path/to/src`.** **You type `cd ..`, then `ls`. What does `ls` print?**" Say what's true, then ask exactly what you want answered — don't make the reader extract the question from a run-on sentence.
- **If a question or activity refers back to an earlier diagram ("using the diagram in section 1…", "the same tree as above"), duplicate that diagram right next to the question instead of making the reader scroll up.** A real bug found this way: two separate activities both said "using the diagram in section 1," forcing a scroll-and-hold-in-memory round trip each time. Copy the SVG (a trimmed/re-highlighted copy is fine, e.g. marking a different "you are here" location for a different question) directly above the activity, and change the reference to "the diagram below." This does mean near-duplicate SVG markup across a few places in the same file — that's the right trade for not making a reader hold a diagram in their head across a scroll.
- **Select-all-that-apply checkbox options need real spacing and a visible border between them, never a bare `<label>` with no margin.** Use `<label class="mlrk-selectall-option"><input type="checkbox" ...> statement text</label>` — the shared class handles the border, padding, and gap. A real bug found this way: several readings had built their own one-off checkbox markup (a bare `<label>`, or a fully inline-styled one, or the `.mlrk-snippet` card class with no margin between cards) and every one of them rendered with zero gap between consecutive options, reading as a cramped wall of text. Also keep each option's statement itself short enough to read in about one line where the content allows — a long compound sentence is harder to evaluate as one true/false unit than a short direct claim, even with good spacing.
- **Don't assume the reader already knows the subject of the reading itself, especially in Mod0/early Mod1 readings where this may be the student's first real exposure to it.** A real bug found this way: a reading about Python's `python`/`python3` command distinction opened by discussing "Python 2's retirement" and "which Python you'd get" without ever stating that Python is the programming language the student is currently learning — fine for someone who already has context, confusing for someone meeting the name for the first time in this exact reading. State the one-sentence version of what the subject *is* before diving into the nuance about it, the same way the company-context rule above applies to companies.
- **Prose should read at a 6th-9th grade Flesch-Kincaid level, outside the technical vocabulary section — 9th grade is a ceiling, not a target to hover under.** The vocabulary flip cards (and any prose actually using/defining those exact terms) are allowed to be as technical as the topic requires — that's the point of teaching the term. Everywhere else, prefer shorter sentences and everyday words over dense or academic phrasing: split compound sentences joined by an em-dash or semicolon into two plain sentences, and cut subordinate clauses ("even though...", "which meant that...") where a period would do. `qa/reading_qa.py` estimates the real Flesch-Kincaid grade automatically (excluding code blocks and the vocabulary section) and WARNs above 9.0 — treat that as a real signal to simplify a sentence, not noise to ignore. Check individual dense paragraphs too, not just the whole-reading average — a scenario built around a real technical incident (an outage, a postmortem) is exactly where jargon like "quota," "null pointer exception," or "feature flag" creeps in unexplained; define the term in plain words the first time it appears, or drop it entirely if it isn't actually needed to teach the target concept (the same "don't assume the reader already knows this" logic as the company/product-context and acronym rules above applies to any unexplained technical term, not just proper nouns).
- **Round a real case study's precise numbers to 2 decimal places for readability, unless the exact figure is itself the point.** A real fix: a scenario used the actual historical multipliers `0.9983` and `1.270589` from a real 2011 pricing-bug story — accurate, but a beginner reader has no reason to parse 4-6 digits of precision to get the point ("one program undercut slightly, the other overpriced substantially"). Rounded to `0.99` and `1.27`, the story reads the same and the contrast is still obvious. This doesn't apply to a number that's inherently exact and meaningful as stated (a dollar total like `$23,698,655.93`, a date, a percentage like `20%`) — round only the kind of long decimal that exists for real-world precision but adds nothing to a reader's understanding of the mechanism being taught.
- **Watch for em-dash overuse and generic "AI tutorial" phrasing** ("in today's digital landscape," "let's dive deep," "it's worth noting," "plays a crucial role," "unlock the power of"). Write like a person explaining something they find genuinely interesting to a friend — personable and a little fun, not a listicle. `qa/reading_qa.py` flags known AI-tell phrases and em-dash pileups (3+ in one line) automatically, but read the prose out loud as a gut check too.
- **Every recommended video must be in English — verify the actual spoken audio via its caption track, never just its title, thumbnail, or channel name.** A real bug found this way: a video titled "Essential Linux Commands: ls, pwd, mkdir, cd, touch, vim, cat" from a channel with an English name and an all-English title had Hindi as its only caption track — the audio was Hindi despite every visible signal reading as English. Title language and audio language are independent; only check the caption track. Run:
  ```bash
  curl -s -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36" "https://www.youtube.com/watch?v=<id>" | grep -o '"captionTracks":\[{"baseUrl":"[^"]*","name":{"simpleText":"[^"]*"},"vssId":"[^"]*","languageCode":"[a-z-]*"' | head -1
  ```
  and confirm the first (default) track's `languageCode` is `en`. `qa/reading_qa.py` now runs this exact check itself over the network (`check_video_language`) and hard-ERRORs on a non-English default caption track — it only falls back to a manual-confirmation reminder when run with `--skip-links`. Also automated: `check_video_embeddable` (a 401 from YouTube's oEmbed endpoint means the owner disabled embedding — shows as "Error 153" in the player) and `check_video_duration` (the 5-minute cap above). Run the full QA pass (no `--skip-links`) at least once before shipping any reading with a video, specifically so these three checks actually execute.

## Structure of a reading
No numbered "Recall" section, otherwise similar shape to the DA readings:

1. **Header**: eyebrow ("Interactive reading"), `<h1>` title, meta pills (estimated time, "Interactive", etc.) — **no scenario text here.** The lead paragraph under the title, if you use one at all, is a single short sentence at most (what the reading covers, not the story) — never a scenario preview. Telling the scenario once, concisely, in section 1 is the whole opening; a longer teaser under the title just makes the reader read the same story twice.
2. **Section 1 opens directly with the scenario** — what happened (real event or realistic simulation), why it's relevant to the reader, and what question/problem the rest of the reading is going to answer using the target topic, told **once, concisely** (a few sentences, not several paragraphs of scene-setting). This doubles as the "why does this matter" hook; don't write a separate generic "why this matters" paragraph on top of it, and don't re-tell or elaborate on the same scenario again later in the reading — establish it once, then move straight into teaching the mechanism.
3. **Vocabulary** (flip cards) — only the terms actually needed for this topic, not an exhaustive glossary.
4. **Teach the mechanism** — the actual explanation, with a real diagram (inline SVG, screenshot-verified) when the relationship between parts is genuinely hard to hold in your head, plus at least one hands-on activity (fill-in-the-blank code, a terminal simulator, a predict-the-output check, a drag-drop, etc.) woven directly into the explanation rather than bolted on at the end.
5. **A short video**, only if a genuinely good, verified-short one exists for this exact topic.
6. **One more practice activity** of a different type than step 4's, to hit the activity-variety bar without padding the reading long.
7. **Quick close**: 1-2 sentence summary + one real critical-thinking or reflection question (free response, `data-save` so it's captured by "Copy Plain Text Answers"). Never phrase this as a "bridge" to anything else.
8. **"Go further (optional)"**: the last content section in the reading — after Summary & reflection, immediately before the score chip/export block — linking to exactly 2 external resources that are NOT another written article — a hands-on tool/practice site (Python Tutor, CodingBat, a real code sandbox), a coding game, or a second video distinct from any embedded earlier in the reading. Every link must be verified for real before it ships: fetch it (`curl -s -o /dev/null -w "%{http_code}" -A "Mozilla/5.0 ..." "<url>"`, expect 200) and, for a video, run the same duration + caption-language check as the embedded-video rule above (it doesn't have to fit the 5-minute cap since it's optional and outside the timed activities, but it must still genuinely be English and on-topic). Markup:
   ```html
   <section class="mlrk-section">
   <h2>N. Go further (optional)</h2>
   <p>Want more practice or a different explanation of this? Two places to go next:</p>
   <ul>
     <li><a href="https://real-verified-url" target="_blank" rel="noopener">Resource Title</a> — one sentence on what it is and why it's useful here.</li>
     <li><a href="https://real-verified-url-2" target="_blank" rel="noopener">Resource Title 2</a> — one sentence on what it is and why it's useful here.</li>
   </ul>
   </section>
   ```
   Doesn't count toward the reading's stated time estimate — it's optional and outside the timed activities. It goes last, after the summary/reflection, not before it — a student closes out the required content first, then sees the optional "if you want more" links on their way to the score chip.
9. **Score chip** (`ReadingKit.Scoring.renderChip`) + **Copy Plain Text Answers** and **Download as .txt** buttons side by side in one `.mlrk-actions` row (`ReadingKit.copyPlainText` + `ReadingKit.downloadPlainText`) + copyright footer.

## Time estimate methodology (10-15 min ceiling, video included)
Build the top-of-page time pill from real counts:
- ~40 seconds per quiz/question-style item.
- ~90 seconds per hands-on activity (flip-card set, drag-drop, order-the-steps, terminal run, fill-in-the-blank).
- ~90 seconds per free-response box.
- The video's actual verified duration.
- ~2-3 minutes baseline for reading the scenario/explanation prose itself.

Add it up. If it's over 15, cut something — don't shrink the displayed number to hide an honest overage. A typical reading here should land around 3-5 quiz/activity items total (not the 15-20+ item readings the DA fellowship builds) — this format is intentionally lean.

## Pipeline
1. **Scope the topic** against this repo's README/existing readings so two readings don't cover the same mechanism.
2. **Pick the real-world scenario** — a real named event/product or a realistic simulation, tied directly to the mechanism being taught.
3. **Author `index.html`** at `Mod<N>/<topic-slug>/index.html` (module numbers 0/1/2 mirror this fellowship's own curriculum: Mod0 = command line/environment/git, Mod1 = Python fundamentals, Mod2 = basic OOP), using `assets/brand-tokens.css` + `assets/reading-kit.css` + `assets/reading-kit.js`. Write a sidecar `reading.meta.json`: `{title, skill, topic_area, time_minutes}` — `skill` is the one specific thing this reading teaches, short and lowercase (`"loops"`, `"dictionaries"`, `"inheritance"`, `"UML diagrams"`), one or two words, never a sentence; `topic_area` is the broader grouping label (`"Python Fundamentals"`, `"Object-Oriented Programming"`) used to section the README/landing page. Both are required — `qa/reading_qa.py`'s `check_meta_sidecar` ERRORs if either is missing.
