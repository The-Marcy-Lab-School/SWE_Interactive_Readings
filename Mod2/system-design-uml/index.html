The Whiteboard Diagram That Kept Two Classes in Sync

~13 minutes Interactive No setup needed to read

1. Two engineers, one checkout feature

Priya and Diego both work on Marcy Library's app. They're splitting a new checkout feature: Priya is building LibraryItem, the base class every item the library lends will share. Diego is building Book, which needs everything LibraryItem has, plus a few things only books need. If they each start typing Python right now, on separate laptops, there's a real risk they invent two slightly different versions of the same idea — say, Priya calls a field is_checked_out while Diego's code assumes it's called checked_out. Neither notices until they try to merge their code and nothing fits together.

So before either of them writes a line of Python, they hop on a call and sketch the class structure together on a shared doc. Engineers have a standard way to draw this out called UML (Unified Modeling Language) — a shared set of boxes and arrows for sketching a design so two people can agree on it before any code exists. It takes them ten minutes, and it's not code — it's a plan they can both sign off on first.

3. Reading a UML class box

Every UML class box has the same three stacked sections, top to bottom: the class's name, then its attributes, then its methods. Here's the LibraryItem class Priya is building, with the Book class Diego is building underneath it, connected by an inheritance arrow:

Reading the top box: LibraryItem is the class name, sitting alone in the top compartment. The middle compartment lists its attributes — each one written as name: type, so title: str means every LibraryItem stores a title that's a string. The bottom compartment lists its methods — each one written as name(): returnType, so check_out(): None means calling check_out() takes no listed input and hands nothing back. None of this is code. It's a plan for code that hasn't been written yet.

The line connecting the two boxes is the inheritance arrow. It's drawn as a plain line ending in a triangle with nothing filled in — you can see the diagram's background right through it. That hollow triangle is the whole rule to remember: it always points at the parent, no matter which direction the line happens to run. Here it points at LibraryItem, so the diagram is saying "Book inherits from LibraryItem," never the other way around.

7. Summary & reflection

A UML class box always stacks the same three things: name on top, attributes in the middle, methods on the bottom. An inheritance arrow is a line ending in a hollow triangle that points at the parent class. Priya and Diego didn't need to write any Python to agree that Book inherits from LibraryItem, adds author and isbn, and defines get_citation() — the diagram said all of that on its own, before either of them opened an editor.
