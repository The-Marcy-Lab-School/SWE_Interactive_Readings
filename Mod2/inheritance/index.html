One Employee Class, Two Different Paychecks

~10 minutes Interactive No setup needed to read

1. The payroll script that grew two heads

Northgate is a mid-size company with two kinds of employees on payroll: hourly workers and salaried workers. Here's what a first, no-inheritance attempt at its payroll script looks like — two classes, written independently:

class HourlyWorker:
    def __init__(self, name, employee_id, hourly_rate, hours_worked):
        self.name = name
        self.employee_id = employee_id
        self.hourly_rate = hourly_rate
        self.hours_worked = hours_worked

    def describe(self):
        return f"{self.name} (ID {self.employee_id})"

    def calculate_pay(self):
        return self.hourly_rate * self.hours_worked


class SalariedWorker:
    def __init__(self, name, employee_id, annual_salary):
        self.name = name
        self.employee_id = employee_id
        self.annual_salary = annual_salary

    def describe(self):
        return f"{self.name} (ID {self.employee_id})"

    def calculate_pay(self):
        return self.annual_salary / 26

The name/employee_id setup and the describe() method are typed out twice, word for word. If Northgate ever changes how an ID is formatted, or what a pay stub description says, someone has to edit both classes and keep them matching. Forget one, and that's a bug waiting to happen. The two classes aren't actually unrelated: both are employees, sharing real data and behavior, with only the pay math genuinely different. That relationship is exactly what class inheritance is for.

3. One parent, two children

The fix starts with a single Employee class holding everything every employee has in common:

class Employee:
    def __init__(self, name, employee_id):
        self.name = name
        self.employee_id = employee_id

    def describe(self):
        return f"{self.name} (ID {self.employee_id})"

    def calculate_pay(self):
        return 0

Then HourlyEmployee becomes a child class of Employee — written as class HourlyEmployee(Employee): — instead of a standalone copy:

class HourlyEmployee(Employee):
    def __init__(self, name, employee_id, hourly_rate, hours_worked):
        super().__init__(name, employee_id)
        self.hourly_rate = hourly_rate
        self.hours_worked = hours_worked

    def calculate_pay(self):
        return self.hourly_rate * self.hours_worked

Three things happen here. HourlyEmployee never redefines describe() at all — it inherits that method from Employee completely unchanged, for free. It overrides calculate_pay(), because the parent's version (always returns 0) is wrong for an hourly worker, so the child's version replaces it. And its __init__ skips retyping self.name = name and self.employee_id = employee_id. Instead it calls super().__init__(name, employee_id) — that means "run Employee's own setup with these two values." Then it adds the two attributes that are new to hourly workers.

Once a HourlyEmployee exists, calling either method just works. Python looks for calculate_pay() on HourlyEmployee first and finds the override. It looks for describe() on HourlyEmployee too, doesn't find it there, and walks up to Employee automatically:

cashier = HourlyEmployee("Priya", "E-104", 18.50, 32) print(cashier.describe()) print(cashier.calculate_pay()) Priya (ID E-104) 592.0

7. Summary & reflection

class Child(Parent): gets every attribute and method the parent defines without retyping any of it. A child overrides a method only when its behavior genuinely needs to differ, and calls super().__init__(...) to still run the parent's setup instead of duplicating it. Northgate's two employee classes went from two full copies of the same setup code to one shared parent and two small, honest differences.
