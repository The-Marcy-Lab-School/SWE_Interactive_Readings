One Call, Three Answers

~11 minutes Interactive No setup needed to read

1. Same call, three different employees

Kettle & Co. is a coffee shop, and its staff app tracks who's working each shift. Here are the classes behind that app. Barista, ShiftLead, and Manager are each a subclass of a shared Employee class — a more specific version of it, that inherits its stuff but can replace any piece of it with its own version:

class Employee:
    def __init__(self, name):
        self.name = name

    def describe(self):
        return f"{self.name} is a staff member."


class Barista(Employee):
    def describe(self):
        return f"{self.name} is a barista who pulls the espresso shots."


class ShiftLead(Employee):
    def describe(self):
        return f"{self.name} is a shift lead who counts the register at closing."


class Manager(Employee):
    def describe(self):
        return f"{self.name} is a manager who handles payroll and scheduling."

Each subclass defines its own describe() — same method name as the one already sitting on Employee, rewritten with its own body. That's called method overriding: when a subclass defines a method with the exact same name as its parent's, its own version wins for objects of that subclass. Now watch what happens when the app builds a list of today's staff and prints a description of each one, using one identical line of code every time:

staff = [Barista("Ana"), ShiftLead("Jordan"), Manager("Priya")]

for employee in staff:
    print(employee.describe())
Ana is a barista who pulls the espresso shots.
Jordan is a shift lead who counts the register at closing.
Priya is a manager who handles payroll and scheduling.

The loop never checks anyone's job title. It calls .describe() on whatever object happens to be sitting in employee that time through the loop, and each object answers with its own class's version — because Python looks up which describe() to run based on the object's actual class, not based on the line of code doing the calling. That's polymorphism: the same method name, called the same way, taking a different, correct form depending on which object it's actually called on.

4. The print() nobody could read

Kettle & Co.'s manager wanted a quicker version of the shift report — just print each employee object directly, no .describe() call:

for employee in staff:
    print(employee)

Here's what actually showed up in the terminal:

<__main__.Employee object at 0x7f9a2c010be0>
<__main__.Employee object at 0x7f9a2c010c40>
<__main__.Employee object at 0x7f9a2c010cd0>

That's Python's default answer to "what should I show for this object?" — a class name and a raw memory address, useless for a report a human has to read, and not even different enough between the three lines to tell who's who at a glance. Here's the part that matters: print() didn't invent that text on its own. Under the hood, print() always calls the object's __str__() method and displays whatever it returns. None of Employee, Barista, ShiftLead, or Manager define one, so Python falls back to its own generic default.

The fix is exactly the same move as describe(): write a method with that name, and Python uses it instead. Add __str__ to Employee:

class Employee:
    def __init__(self, name):
        self.name = name

    def describe(self):
        return f"{self.name} is a staff member."

    def __str__(self):
        return f"Employee: {self.name}"

Now print(employee) shows Employee: Ana instead of a memory address — readable, but it lost the specific-role detail describe() had. Fix that the same way you'd fix any parent-class behavior that's too generic for one particular subclass: override it there too. Add a more specific __str__ just to ShiftLead:

class ShiftLead(Employee):
    def describe(self):
        return f"{self.name} is a shift lead who counts the register at closing."

    def __str__(self):
        return f"{self.name} (Shift Lead)"

With only ShiftLead overriding it, printing the same staff list now shows a mix — every object still uses whichever __str__ actually belongs to its own class, inherited or overridden:

Employee: Ana
Jordan (Shift Lead)
Employee: Priya

__str__ is a dunder method: its double-underscore name is Python's signal that this one is special, called automatically by print() rather than by you typing .__str__() yourself. Everything else about it — writing it in a class, overriding it in a subclass — works exactly like describe().

6. Summary & reflection

Kettle & Co.'s report worked because Barista, ShiftLead, and Manager each overrode describe() with their own version — one call, three correct answers, with no type-checking anywhere. __str__ runs on the same rule, except print() calls it for you automatically, which is what makes it a dunder method instead of an ordinary one.
