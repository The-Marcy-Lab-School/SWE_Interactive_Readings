Don't Reach Past the Teller

~12 minutes Interactive Builds on classes & objects

1. The rule the class is supposed to guarantee

PocketVault is a fictional personal-banking app built around one class, BankAccount. Every account object keeps track of its own balance in an attribute called _balance, and the class exists to guarantee exactly one rule: that balance can never go negative. Here's the class, roughly as PocketVault's engineers wrote it:

class BankAccount:
    def __init__(self, starting_balance):
        self._balance = starting_balance

    def withdraw(self, amount):
        if amount <= self._balance:
            self._balance -= amount
        else:
            print("Insufficient funds")

withdraw() checks first, before it changes anything: is there enough money to cover this? Only if that check passes does self._balance actually change. That single if statement is the whole reason the rule holds. Skip it, and there's nothing left protecting the balance at all. (The class also defines a matching deposit() method for adding funds through that same kind of guarded path — this reading focuses on withdraw(), since that's where the rule actually needs protecting.)

Last quarter, a different engineer wrote a one-off script to process a batch of overnight vendor payouts. Under deadline pressure, instead of calling withdraw() for each payout, the script went straight for the attribute:

for payout in pending_payouts:
    account = accounts[payout.account_id]
    account._balance -= payout.amount

That line runs perfectly fine in Python every single time, whether or not payout.amount is bigger than whatever is actually in the account. Nothing in the language stops it. By morning, several PocketVault accounts had gone negative — not because of a math error, but because the one line of code that was supposed to check first never ran at all.

3. The underscore isn't a lock

The leading underscore in _balance is not decoration. It's Python's naming convention for exactly this situation: a single leading underscore tells any other programmer reading the code, "this is internal to the class — don't set it directly from outside." self._balance could just as easily have been named self.balance, with no underscore at all, and Python would run either version identically. The underscore is a signal aimed at people, not a rule enforced by the interpreter.

That's exactly the gap the payout script fell into. Nothing about _balance stopped that script from reaching in and changing it directly. The underscore asked politely, and the script ignored it.

True or false: if outside code writes account._balance = -500, Python raises an error and refuses the assignment.

4. Write the one sanctioned door in

The fix for PocketVault was never a smarter underscore or a stronger warning comment — Python has no setting that makes an attribute truly private. The fix is a habit: every piece of code that changes _balance, including the class's own code, goes through a method that can check something first. withdraw() above is that method already. 7. Summary & reflection

PocketVault's _balance was never actually locked. The leading underscore only ever asked other code to leave it alone, and the class's real protection lived entirely inside withdraw()'s if check. Any class that needs to guarantee a rule about its own state has to route every change through a method that can enforce that rule, because a naming convention alone stops nothing.
